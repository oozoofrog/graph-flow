## 배경

구현하는 동안 코드와 명세가 서로 멀어질 수 있습니다. 알게 된 차이를 그대로 두면 의도 부채가 생깁니다. 어느 쪽이 의도한 동작인지 아무도 말할 수 없게 됩니다. 명세가 틀리고 코드가 옳을 때도 있습니다. 설계 리뷰에서 한 사례가 나왔습니다. CEM-R7은 1등급 검사 결과를 예측하라고 했지만, 게이트는 1등급 실패를 사람에게 묻기 전에 반려합니다. [gate.py](../../skills/graph-flow/scripts/graphflow/gate.py) · [Storey](https://arxiv.org/abs/2603.22106)

## 결정

코드는 명세를 따릅니다. 코드와 명세가 다르면 기본적으로 코드를 고칩니다. 다음 세 이유 가운데 하나로 코드가 옳을 때만 명세를 바꿉니다.

| 이유 | 뜻 |
| --- | --- |
| 에이전트의 제한 | 에이전트가 능력이나 지켜야 할 규칙 때문에 명세대로 만들 수 없습니다. |
| 코드 자체의 한계 | 언어, 플랫폼, 실행 환경, 기존 시스템이 명세대로의 동작을 막습니다. |
| 기능 향상 | 코드가 명세보다 나은 동작을 냅니다. |

명세 변경에는 이유와 증거를 적습니다. 에이전트는 명세 변경을 미확인 항목으로 제안합니다. 사람이 명세 개정을 받아들입니다. 알게 된 차이를 해소하지 않은 채 두지 않습니다. 변경이 차이를 해소할 때까지 요구와 코드 사이에 `conflicts with` 연결을 기록합니다. [명세 절차](../spec/README.ko.md#코드는-스펙을-따른다) · [ADR 0003](0003-keep-link-confirmation-with-the-person.ko.md)

## 검토한 대안

코드만 기준으로 삼으면 명세는 아무도 믿지 않는 요약이 됩니다. 명세만 기준으로 삼으면 에이전트가 시스템이 감당할 수 없거나 더 나쁜 동작을 만들어야 합니다. 어느 방향이든 말없이 고치면 이유를 잃습니다.

## 결과

차이는 모두 이유가 기록된 채 한 방향으로 해소됩니다. 명세는 목표일 뿐 아니라 사람의 이해가 어떻게 바뀌었는지를 보여 주는 기록이 됩니다. 명세 변경은 사람의 검토 일을 늘립니다. 이 규칙은 지도를 구현할 때 graph-flow 원칙 P13이 됩니다.
