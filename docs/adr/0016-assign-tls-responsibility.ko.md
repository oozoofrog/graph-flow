# 0016 TLS 책임을 설정된 엔드포인트에 맡긴다

상태: 제안됨(Proposed)

## 배경

사설 경로는 누가 접속할 수 있는지를 정합니다. 실수로 공개 경로가 생기면 같은 엔드포인트가 노출될 수 있습니다.
소유자에게는 패스키 검증에 쓸 안정된 HTTPS 오리진과 신뢰 당사자 ID가 필요합니다. 로컬 대시보드는 자기 루프백 Host만 받아들입니다.
Python은 서버 쪽 TLS 컨텍스트와 인증서 불러오기 기능을 제공합니다. [대시보드](../../skills/graph-flow/references/dashboard.md) · [Python SSL 컨텍스트](https://docs.python.org/3/library/ssl.html#ssl-contexts)

## 결정

명시적인 authority를 가진 외부 HTTPS 오리진 하나와, 소유자가 고른 인터페이스 주소 하나를 설정합니다.
IPv4와 IPv6 와일드카드를 포함해 와일드카드 주소는 거부합니다. 그 인터페이스가 사라져도 자동으로 다른 주소에 바인딩하지 않습니다.
아래 전송 방식 가운데 하나를 씁니다. OQ-3은 어느 방식을 먼저 내놓을지를 다룹니다.

| 방식 | 책임 |
| --- | --- |
| 직접 TLS | 소유자가 인증서와 키를 준비하고 갱신합니다. 원격 리스너가 선택한 주소에서 HTTPS를 제공합니다. |
| 리버스 프록시 | 소유자가 프록시의 HTTPS 엔드포인트와 인증서를 설정합니다. 프록시는 원격 경로만, 상호 인증 TLS로 전용 루프백 백엔드에 전달합니다. |

프록시 방식에서는 허가된 프록시 클라이언트 자격 증명을 고정하고, 프록시에서 백엔드 인증서를 검증합니다.
프록시 자격 증명은 공유 계정 밖에 둡니다. 일반 대시보드는 그 프록시를 거치지 않게 합니다.
애플리케이션에서 설정된 외부 Host와 Origin을 요구합니다. 외부 Host는 명시적으로 전달합니다.
클라이언트가 보낸 전달 헤더는 버립니다. 백엔드 접근 여부는 인증된 연결로 판단합니다.
실제 클라이언트 주소 기준의 출처별 한도는 프록시에 둡니다. 기기별 한도와 설치본 한도는 두 방식 모두 애플리케이션에서 적용합니다.
직접 연결에서는 애플리케이션의 출처별 한도를 씁니다. 주장된 전달 주소로 권한을 정하지 않습니다.
읽기 세션은 수명을 짧게 하고 URL에 넣지 않습니다. 비용이 큰 검증 작업에 자원을 할당하기 전에, 아직 남은 요청 수와 확인 요청 저장량을 제한합니다.
인증서 만료와 호스트 이름 검사에는 검증하는 클라이언트를 씁니다. 핸드셰이크가 실패해도 HTTP로 대체하지 않습니다.

## 검토한 대안

사설 네트워크에서 평문 HTTP를 쓰면 기밀성이 그 네트워크에 달리고, 일반적인 원격 WebAuthn 보안 컨텍스트를 쓸 수 없습니다.
평문 루프백 백엔드에서 프록시 헤더를 믿으면 로컬 호출자가 프록시를 흉내 낼 수 있습니다.
네트워크 제공자 하나를 요구하면 다른 사설 경로를 쓰는 소유자가 빠집니다.

## 결과

직접 TLS에는 인증서 발급이 필요합니다. 프록시를 쓰면 믿어야 할 구성 요소와 인증서 관계가 하나씩 더 생깁니다.
인증서가 만료되거나, 인터페이스에 닿을 수 없거나, 프록시가 멈춰도 로컬 대시보드는 쓸 수 있습니다.
엔드포인트가 공개적으로 접근 가능해져도 세션 인증과 답변별 검증은 그대로 적용됩니다.
공격 중에는 한도 때문에 정상적인 원격 요청이 늦어질 수 있습니다. 한도가 가용성을 보장하지는 않습니다.
검증하는 브라우저는 TLS 엔드포인트까지의 연결을 보호합니다. TLS를 종료하는 프록시가 침해되면 그 프록시는 페이지를 보거나 바꿀 수 있습니다.
