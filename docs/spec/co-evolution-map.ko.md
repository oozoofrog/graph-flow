> 이 문서는 [co-evolution-map.md](co-evolution-map.md)의 한국어 읽기본입니다. 기준은 영어 원문입니다.
> 원문 해시: `sha256:a1059feb63e8a831af8afee84630098cbb2ea7c49ea2b6a0eb551b40f3a8341e`. 영어 원문이 바뀌면 `scripts/tests/test_reading_copies.py`가 실패합니다.
> 요구 ID와 의무 강도는 원문과 같습니다. 의무 강도는 한국어 표현 뒤에 원문 키워드를 함께 적습니다.

상태: 초안(Draft)

## 목적과 범위

사람은 생각 하나를 그것을 구현한 코드까지 따라갈 수 있습니다. 에이전트는 같은 경로를 거꾸로 따라가 사람이 그렇게 정한 이유에 닿을 수 있습니다. 둘은 함께 선택을 따져 보고, 용어를 바꾸고, 예상을 시험합니다. 공진화는 도구와 사람의 일하는 방식이 함께 나아지는 것을 뜻합니다. [Engelbart](https://dougengelbart.org/content/view/116/)

인지 부채는 팀이 자기 시스템에 대한 이해를 잃을 때 쌓입니다. 의도 부채는 선택의 이유가 사라질 때 쌓입니다. 지도는 사람이 그 이유를 되찾고 따져 볼 자리를 줍니다. [Storey](https://arxiv.org/abs/2603.22106)

첫 범위는 프로젝트 하나와 그 프로젝트의 로컬 실행입니다. 다음은 범위 밖입니다.

- 실행 제어
- 에이전트 감시
- 사람에게 자동으로 점수 매기기
- 프로젝트를 넘나드는 승인

이슈 #3이 여러 실행을 모은 요약을 제공합니다. 이슈 #5가 제안된 기능 네 가지를 제공합니다. 예측, 교훈 확인, 요약 지표는 이슈 #3 다음에 만듭니다. 반론 기능은 이 셋으로 기준 수치를 모은 뒤에 시험합니다. [이슈 #3](https://github.com/oozoofrog/graph-flow/issues/3) · [이슈 #5](https://github.com/oozoofrog/graph-flow/issues/5)

## 용어

- **지도 노드(map node):** 주소로 가리킬 수 있는 항목입니다.
- **연결(link):** 두 지도 노드 사이의 방향이 있는 진술입니다.
- **경로(trail):** 읽는 사람이 어느 방향으로든 따라가는 연결의 순서입니다.
- **출처 참조(source reference):** 프로젝트, 출처, 항목, 그리고 해당 버전이나 시도를 가리킵니다.
- **사람 단계(human slot):** 결정, 승인, 실행 종료처럼 이미 있는 사람의 차례입니다.

[Bush](https://www.w3.org/History/1945/vbush/vbush7.shtml)

| 지도 노드 종류 | 뜻 |
| --- | --- |
| 생각 (Thought) | 작성자가 남기기로 한 아이디어나 열린 질문 |
| 지시 (Instruction) | 사람이 작업에 대해 준 방향 |
| 명세 (Spec) | 기대하는 동작을 적은 문서 |
| 요구 (Requirement) | 명세나 계획 안에서 고정 ID를 가진 의무 하나 |
| 도메인 용어 (Domain term) | 한 분야 안의 개념 하나에 붙인 이름과 정의 |
| 계획 (Plan) | 한 실행의 약속을 기록한 버전 하나 |
| 계획 노드 (Plan node) | 그 계획 안의 단위 하나. 종류는 `work`, `review`, `decision` |
| 결정 (Decision) | ADR 하나, 또는 기록된 상태와 답을 가진 실행 중 질문 하나 |
| 교훈 (Lesson) | 이유와 다음 재검토 조건을 가진 깨달음. 계획용 제약은 교훈의 출처 가운데 하나 |
| 파일 (File) | 특정 버전이나 제출에서의 프로젝트 기준 경로 |
| 커밋 (Commit) | 저장소와 전체 객체 ID로 가리키는 Git 변경 |
| 검사 (Check) | 기준과, 선택한 시도의 결과를 가진 이름 붙은 시험 |

연결은 주어에서 목적어 방향으로 읽습니다. 아래 표가 연결 종류의 전부입니다. 연결마다 그 둘이 왜 이어지는지를 이유로 적습니다.

| 연결 종류 | 주어 → 목적어 | 뜻 |
| --- | --- | --- |
| 포함 (contains) | 명세나 계획 → 요구, 또는 계획 → 계획 노드 | 출처가 이 구성원을 담고 있습니다. |
| 다룸 (addresses) | 계획 노드 → 요구 | 계획이 이 의무를 이 단위에 맡깁니다. |
| 용어 사용 (uses term) | 모든 지도 노드 → 도메인 용어 | 이 개념이 그 분야에서 주어를 설명합니다. |
| 동기 (motivates) | 생각, 지시, 결정, 교훈 → 모든 지도 노드 | 주어가 목적어의 이유가 됩니다. |
| 변경 (changes) | 커밋 → 파일 | 커밋이 이 경로의 변경을 기록합니다. |
| 제출 (submits) | 계획 노드 → 커밋이나 파일 | 제출물이 이 커밋을 가리키거나 이 파일을 적습니다. |
| 검사 (tests) | 검사 → 계획 노드, 계획, 요구 | 검사 기준이 목적어의 특정 성질을 확인합니다. |
| 근거 (draws from) | 교훈이나 결정 → 모든 지도 노드 | 주어가 목적어를 근거로 인용합니다. |
| 충돌 (conflicts with) | 모든 지도 노드 → 모든 지도 노드 | 작성자는 두 항목이 적힌 그대로는 함께 성립할 수 없다고 봅니다. |
| 관계 (relates to) | 모든 지도 노드 → 모든 지도 노드 | 작성자가 다른 종류에 들지 않는 연결을 설명합니다. |

**예.** 사람이 *원본 노트*를 "내보낸 뒤에도 노트북에 남는 노트"로 정의합니다. 요구 *내보내기는 원본 노트를 보존한다*가 이 용어를 씁니다. 계획 노드 *내보내기 작성*이 이 요구를 다룹니다. 이 노드는 내보내기 코드를 바꾸는 커밋을 제출합니다. 검사가 실패하면 사람은 "첨부 파일도 원본 노트에 속하는가?"라는 질문을 떠올릴 수 있습니다.

## 출처와 새 기록

| 정보 | 출처와 규칙 |
| --- | --- |
| 계획과 작업 | 계획 버전, `requirements`, `requirement`, 검사 정의를 읽습니다. 계획 ID는 그 실행 안에서 그대로 유지합니다. |
| 결과와 이유 | 제출, 커밋, 검사 등급, 리뷰 지적, 결정 맥락, 답변, 범위가 정해진 반려를 씁니다. 경로가 선언되었다는 사실만으로는 변경의 증거가 되지 않습니다. |
| 교훈 | 제약의 글, 범위, `derived_from`, `review_when`, 상태를 읽습니다. 개인 교훈은 계획에 영향을 주지 않습니다. |
| 설계 | 명시적으로 참조한 명세, ADR, 도메인 정의를 인용된 버전 그대로 읽습니다. |
| 새로 작성한 것 | 고른 생각, 지시, 정의, 개인 교훈, 연결의 버전을 작성자와 출처 참조와 함께 보관합니다. 이미 있는 출처를 되도록 다시 씁니다. |
| 새로운 개인 선택 | 예측, 건너뛰기, 교훈 확인, 연결 확인에는 기존 결정 답변을 씁니다. 해당 답변과 항목 버전을 가리키는 참조를 저장합니다. |
| 파생 결과 | 지도 노드, 출처 관계에서 나온 연결, 역방향 조회, 지표를 다시 만듭니다. 생성된 색인은 그 자체로 권위가 없습니다. |

**파생 연결(derived link)** 은 출처에 명시된 관계를 그대로 옮긴 것입니다. 기계적으로 이은 연결은 근원으로 출처 필드의 이름을 적습니다. **작성 연결(authored link)** 은 사람의 해석이나 에이전트의 제안을 기록합니다. 글이 비슷하거나 시간이 가깝다는 것만으로는 파생 연결이 생기지 않습니다. 사라진 버전을 인용하는 연결은 원래 출처 참조를 그대로 유지합니다. [Records](../../skills/graph-flow/references/records.md) · [ADR 0002](../adr/0002-derive-the-map-from-source-records.md)

## 요구

이 문서의 의무 표현은 BCP 14([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174))를 따릅니다. 원문 키워드를 괄호 안에 함께 적습니다.

| 원문 키워드 | 이 문서의 한국어 표현 |
| --- | --- |
| MUST | 반드시 …해야 한다 |
| MUST NOT | …해서는 안 된다 |
| SHOULD | …하기를 권장한다 |
| MAY | …해도 된다 |

### CEM-R1 — 출처에서 다시 만들기

같은 출처 버전과 작성 기록에서는 반드시 같은 지도 노드와 연결이 나와야 한다(MUST). 사라진 출처는 반드시 "사용할 수 없음"으로 표시해야 한다(MUST).

확인: 두 실행에 같은 로컬 ID가 있는 상태로 두 번 다시 만듭니다. 종류가 붙은 양 끝과 출처 참조를 비교합니다. 출처 하나를 지우고 표시를 확인합니다.

### CEM-R2 — 용어에서 양방향으로 따라가기

지도는 반드시 용어 표의 모든 종류를 지원해야 한다(MUST). 읽는 사람은 보이는 연결을 어느 방향으로든 따라가고 그 이유와 출처 참조를 볼 수 있어야 한다(MUST).

확인: 모든 종류를 담은 시험 자료를 씁니다. 위의 예를 도메인 용어에서 파일까지 갔다가 되돌아옵니다. 두 방향이 같은 연결 ID를 쓰는지 확인합니다. [ADR 0004](../adr/0004-use-the-domain-glossary-as-an-entry-point.md)

### CEM-R3 — 연결의 출처 남기기

지도는 반드시 연결의 근원과 확인 이력을 보관해야 한다(MUST). 사람은 반드시 이유를 적어 연결을 직접 만들 수 있어야 한다(MUST). 에이전트의 제안은 사람이 그 연결 버전을 명시적으로 확인하기 전까지 반드시 미확인 상태여야 한다(MUST). 기본 경로 화면은 파생 연결, 사람이 만든 연결, 확인된 에이전트 제안을 반드시 구분해야 한다(MUST). 미확인 제안은 반드시 따로 보여야 한다(MUST).

지도는 "사람이 만듦" 표시와 확인 상태를 반드시 해당 항목 버전에 대한 검증된 증거에서만 얻어야 한다(MUST). 검증된 증거는 검증을 통과한 실행 안 답변입니다. 파일 안에 적힌 주장은 증거가 아닙니다. 지도는 검증된 증거 없이 항목을 확인된 것으로 다뤄서는 안 된다(MUST NOT).
대기열에 들어간 선택에 대해서는 지도가 반드시 CEM-R6의 issuer, purpose, evidence, 정확한 답변 형식을 요구해야 한다(MUST).
지도는 반드시 제안자를 보관하고, 거절을 확인된 경로 밖의 이력에 기록해야 한다(MUST).
인용된 확인에 원래 검증 맥락이 없으면, 지도는 반드시 CEM-R14의 상태를 보여 줘야 한다(MUST). 확인된 항목의 이유나 양 끝이 바뀌면 그 항목은 반드시 다시 미확인이 되어야 한다(MUST).

선택한 프로젝트 시점에서 미확인 제안이 인용한 출처가 바뀌었으면, 지도는 반드시 그 제안을 철회해야 한다(MUST). 철회된 제안은 반드시 이력에 남아야 한다(MUST). 이전 시점을 다시 볼 때는 반드시 그 시점의 상태를 보여야 한다(MUST).

확인: 사람이 연결 하나를 만듭니다. 그 표시를 파생 연결, 에이전트 제안과 비교합니다. 계획 승인만으로는 제안이 미확인으로 남는지 확인합니다. 제안 하나를 확인합니다. 그 이유를 고치고 다시 확인이 필요한지 봅니다. 증거 없이 "사람이 만듦"이라고 적은 파일을 더합니다. 계획에서 `gf map check`를 빼고 미확인 표시가 나오는지 봅니다. 미확인 제안이 인용한 출처를 바꾸고 그 제안이 이력으로 옮겨지는지 봅니다. 이전 시점을 다시 보고 원래 상태가 나오는지 봅니다. [ADR 0003](../adr/0003-keep-link-confirmation-with-the-person.ko.md)

### CEM-R4 — 사람의 언어로 쓰기

모든 지도 노드와 연결에는 반드시 사람의 언어로 된 쉬운 이름과 설명이 있어야 한다(MUST). 설명이 없으면 반드시 "빈칸" 표시가 있어야 한다(MUST). 한국어 읽기본은 반드시 기준이 된 영어 원문 버전을 밝혀야 한다(MUST). 한국어 읽기본은 반드시 요구 ID, 연결의 뜻, 의무 강도를 그대로 지켜야 한다(MUST). 한국어 읽기본은 반드시 영어 원문의 SHA-256 해시를 적어야 한다(MUST). 그 해시가 지금의 영어 원문과 다르면 저장소 테스트는 반드시 실패해야 한다(MUST).

확인: 종류마다 예 하나를 한국어로 봅니다. ID 목록을 기계적으로 비교합니다. 두 언어를 읽는 사람이 의무와 연결의 뜻을 비교합니다. 영어 원문을 바꾸고 `scripts/tests/test_reading_copies.py`가 실패하는지 봅니다. [ADR 0006](../adr/0006-keep-one-english-reference.md)

### CEM-R5 — 사람이 자기 이해를 점검하기

학습 방식은 선택한 경로에 대해 반드시 아래 세 질문을 내야 한다(MUST). 사람은 점수 없이 빈칸을 표시하거나 연습을 건너뛸 수 있어야 한다(MUST).

| 능력 | 사람에게 묻는 질문 |
| --- | --- |
| 해법을 현실과 잇기 | 이 부분은 어떤 실제 일을 돕나요? |
| 선택을 설명하기 | 이 부분은 왜 이렇게 동작하나요? |
| 변화에 대응하기 | 요구가 바뀌면 어느 부분과 어느 검사를 먼저 바꾸나요? |

확인: 사람이 참여하는 시험에서 경로 하나를 자기 말로 설명하게 합니다. 답할 수 있는 질문과 다시 보고 싶은 질문을 기록합니다. 세 질문과 건너뛰기 동작이 있는지는 따로 시험합니다. [Naur](https://gist.github.com/dpritchett/fd7115b6f556e40103ef)

### CEM-R6 — 함께하는 방식을 기존 사람 단계에 얹기

실행 안에서 각 방식은 반드시 아래 표의 사람 단계를 써야 한다(MUST). 네 방식을 모두 건너뛰어도 필수 답변, 멈춤 상태, 판정은 반드시 기준 실행과 같아야 한다(MUST).

| 방식 | 기존 사람 단계 | 사람과 에이전트가 하는 일 |
| --- | --- | --- |
| 학습 | 사람 검사, 3단계, 보류 질문. 실행 종료 | 사람이 결과를 예측합니다. 종료 때 에이전트가 증거를 바탕으로 세 질문을 냅니다. |
| 토의 | 계획 승인이나 실행 종료 | 에이전트가 요구나 교훈의 이유를 인용합니다. 사람은 그 이유를 자기 말로 고칠 수 있습니다. |
| 토론 | 계획을 나누기 전의 기존 방향 결정. 없으면 계획 승인 때의 선택 의견 | 검토자가 원래 분할에 대한 대안과 가장 강한 반론을 냅니다. 사람이 고르거나 다른 방향을 줍니다. |
| 브레인스토밍 | 계획을 나누기 전의 기존 방향 결정, 또는 계획 승인 | 사람과 에이전트가 가능한 접근을 냅니다. 사람은 계획에 넣지 않은 생각도 남길 수 있습니다. |

실행 밖에서 사람이 고르면 반드시 Git으로 관리하는 항목이 `pending confirmation`으로 대기열에 들어가야 한다(MUST).
대기열은 반드시 프로젝트, 항목 ID, 저장소 기준 상대 경로, Git 커밋 ID와 blob ID를 고정해야 한다(MUST).
대기열은 반드시 그 고정 정보와 함께 정확한 파일 바이트의 SHA-256을 저장해야 한다(MUST).
작업 파일이 이미 달라졌더라도 대기열은 반드시 선택한 Git blob을 고정해야 한다(MUST). 선택이 실행 결정을 만들어서는 안 된다(MUST NOT).

다음 실행의 계획 승인이나 실행 종료 때, 리더는 반드시 `gf map present`로 대기열을 제시해야 한다(MUST).
Graph-flow는 반드시 그 사람 단계에서 대기 중인 버전들에 대해 선택 사항인 묶음 하나를 내야 한다(MUST).
다시 제시할 때는 실행 종료 때를 포함해 반드시 이미 열린 묶음을 다시 써야 한다(MUST). 빈 대기열에서는 반드시 결정 없이 끝나야 한다(MUST).
이 명령은 반드시 리더가 쓴 글이나 항목 선택 없이 동작해야 한다(MUST). Graph-flow는 반드시 사람의 언어로 된 고정 템플릿을 써야 한다(MUST).
Graph-flow는 반드시 고정된 각 파일을 Git에서 그대로 읽고, 이유를 포함한 그 내용을 동작하지 않는 증거로 보여 줘야 한다(MUST).
결정은 반드시 `issuer: map`과 `purpose: map_confirmation`을 써야 한다(MUST). 결정의 `evidence`는 반드시 순서가 있는 항목 ID, 경로, Git 참조, 내용 해시를 묶어야 한다(MUST).
현재 파일이 다르거나 사라졌으면, 화면은 반드시 그 항목을 `changed after selection`으로 표시해야 한다(MUST).
답변 경로는 반드시 현재 바이트를 다시 검사하고 그 버전의 확인을 거부해야 한다(MUST). 새 버전에는 새 선택이 필요합니다.
고정된 내용을 쓸 수 없으면 반드시 확인을 비활성화해야 한다(MUST). 인용한 출처가 바뀌면 CEM-R3의 철회 규칙은 그대로 적용됩니다.

로컬 대시보드와 원격 화면은 반드시 버전마다 확인, 대기 유지, 거절 선택지를 주어야 한다(MUST).
두 화면은 확인을 미리 선택해 두어서는 안 된다(MUST NOT). 두 화면은 반드시 사람의 선택으로 답변 글을 만들어야 한다(MUST).
증거 항목마다 ASCII 한 줄을 묶인 순서대로 씁니다. 줄은 LF로 잇고 마지막 LF는 붙이지 않습니다.
각 줄은 동작, 공백 하나, 종류가 붙은 항목 ID, `@`, 내용 해시로 이루어집니다.
SHA-256 해시는 소문자 16진수 64자리로 씁니다.
동작은 `confirm`, `pending`, `reject`입니다. 예를 들어 `confirm link:L12@<hash>`에서는 `<hash>` 자리에 전체 해시를 씁니다.
각 ID 구성 요소는 UTF-8로 인코딩합니다. ASCII 영문자, 숫자, 하이픈, 마침표, 밑줄, 물결표가 아닌 모든 바이트는 대문자 16진수로 퍼센트 인코딩합니다.
종류와 ID 사이에는 콜론 하나를 그대로 씁니다.
지도는 반드시 위의 issuer, purpose, evidence와 맞는 검증된 `answered` 결정 안의 이 형식만 받아들여야 한다(MUST).
지도는 반드시 어떤 선택이든 적용하기 전에 형식이 잘못된 글, 빠지거나 중복된 항목, 남는 항목, 맞지 않는 해시를 거부해야 한다(MUST).
확인은 그 버전에만 적용됩니다. 대기 유지는 그 버전을 대기열에 남깁니다. 거절은 그 버전을 대기열에서 빼고 이력은 남깁니다.
지도는 반드시 검증된 답변을 여러 번 적용해도 결과가 같도록 적용해야 한다(MUST).

묶음이 준비 상태, 판정, 실행 종료를 막아서는 안 된다(MUST NOT).
실행 종료 때 graph-flow는 반드시 종료 트랜잭션 안에서 답하지 않은 묶음마다 `decision.superseded`를 기록해야 한다(MUST).
명시적으로 건너뛰거나 답하지 않으면, 반드시 꾸며 낸 답변 없이 자격이 있는 항목을 대기 상태로 남겨야 한다(MUST).
실행 종료는 반드시 멈춤 결정을 검사하기 전에 답하지 않은 묶음을 대체 처리해야 한다(MUST).
답변과 종료가 경합하면, 트랜잭션은 반드시 결정의 최종 상태를 정확히 하나만 남겨야 한다(MUST). [ADR 0017](../adr/0017-confirm-out-of-run-items-in-the-next-run.ko.md)

확인: 항목 세 개를 대기열에 넣습니다. 두 화면에서 템플릿, 고정된 Git 바이트, 증거, 정규 답변을 확인합니다.
하나는 확인하고, 하나는 대기 상태로 두고, 하나는 거절합니다. 같은 답변을 다시 적용하고 이력을 살펴봅니다.
선택한 뒤 파일을 고치고, 표시한 뒤 다시 고칩니다. 바뀐 버전의 확인이 거부되는지 봅니다.
자유 질문, 중복된 줄, 틀린 해시를 넣습니다. 확인되지 않는지 봅니다.
계획 승인에서 묶음을 건너뛰고 실행을 종료합니다. 답하지 않는 경우, 종료 때 나온 묶음, 경합하는 답변으로 반복합니다.
답하지 않은 묶음마다 대체 이벤트를 살펴봅니다. 종료 뒤 열린 결정이 없는지 봅니다.
함께하는 방식마다 참여한 경우와 참여하지 않은 경우를 다시 돌립니다. 필수 멈춤, 판정, 준비 상태, 최종 상태를 비교합니다.
자발적인 답변은 따로 셉니다. [ADR 0005](../adr/0005-use-existing-human-slots-for-co-work.ko.md)

### CEM-R7 — 증거를 보기 전에 예측하기

해당 게이트에서 사람의 답변 화면은 증거를 보여 주기 전에 반드시 예측이나 건너뛰기를 제시해야 한다(MUST). 예측은 이 단위가 나중에 재작업이 될지를 고르는 것입니다. 재작업은 이 답변 뒤에 기록된 반려, 다시 열기, 되돌림입니다. 화면은 사람의 선택을 반드시 기존 서명 답변 글에 보관하되, 판정이나 설명은 바꾸지 않아야 한다(MUST).

해당 게이트는 위험 신호가 있는 사람 검사, 3단계, 보류 질문입니다. 위험 신호는 같은 단위의 첫 시도, 빨간 검사, 기록된 되돌림 가운데 하나입니다. 다른 게이트는 증거를 바로 보여 줍니다. 사람은 건너뛰어 증거를 곧바로 볼 수 있습니다.

이 과정을 거치지 않은 답변에는 예측 기록이 없습니다. 답변은 단위와 시도를 가리킵니다. 평범한 자유 글은 점수를 매기는 예측이 되지 않습니다. 1등급 검사가 실패하면 게이트는 사람에게 묻기 전에 작업을 반려합니다. 그래서 1등급 검사 결과는 예측 대상이 될 수 없습니다. [gate.py](../../skills/graph-flow/scripts/graphflow/gate.py)

확인: 재작업 예측, 재작업 없음 예측, 건너뛰기, 일반 터미널 답변을 각각 다른 시험 자료로 해 봅니다. 위험 신호가 없는 게이트를 더하고 예측 질문이 나오지 않는지 봅니다. 표시 순서와 답변 글을 확인합니다. 판정이 같은지 봅니다.

### CEM-R8 — 새 교훈마다 확인하기

`gf learn add`가 한 실행에 기록한 제약마다 사람에게는 반드시 선택형 자유 질문이 있어야 한다(MUST). 리더가 최종 게이트 뒤에 더한 제약도 여기에 들어갑니다. 선택지는 반드시 유지, 내 말로 이유 고쳐 쓰기, 버리기를 포함해야 한다(MUST). 답하지 않은 제약도 반드시 그 범위 안에서 계속 적용되어야 하고, 계획 카드에 "확인 안 됨" 표시가 있어야 한다(MUST).

유지나 고쳐 쓰기를 고르면 제약에 결정 ID가 담긴 `ratified_by`가 보입니다. 고쳐 쓰기는 사람의 이유를 원래 제약 옆에 둡니다. 승인된 명령은 바뀌지 않습니다. 버리기는 기존 폐기 절차에서 그 결정을 인용합니다. 변경은 다음 계획부터 적용됩니다. 이전 제약 버전에 대한 서명 답변은 이력으로 남습니다.

확인: 세 선택과 무응답을 모두 해 봅니다. 최종 게이트 뒤에 제약을 더하고 그 질문이 나오는지 봅니다. 다음 계획 카드, 제약 상태, 이유, 결정 참조를 비교합니다. 실행 종료가 답변을 기다리지 않는지, 필수 멈춤이 생기지 않는지 확인합니다. [leader.md 8–9절](../../skills/graph-flow/references/leader.md)

### CEM-R9 — 승인 뒤에 일어난 일을 보여 주기

여러 실행을 모은 `gf summary`는 반드시 아래 지표를 출처 기록에서 계산해 보여야 한다(MUST). 실행 하나의 `gf trace --conformance`는 반드시 예측 적중도와 사람이 확인한 새 제약의 비율을 보여야 한다(MUST).

| 지표 | 세는 규칙 |
| --- | --- |
| 나중의 재작업 | 같은 단위에서 승인 뒤 반려, 다시 열기, 되돌림이 기록된 승인을 셉니다. 승인 하나는 한 번만 셉니다. |
| 짧은 대기 | 질문에서 답변까지 걸린 시간이 그 결정 종류의 기준보다 짧은 승인을 셉니다. 기준은 종류마다 초 단위로 보여 줍니다. |
| 승인 비율 | 종류마다 승인 수를 승인 여부가 있는 답변 수로 나눕니다. |
| 예측 적중도 | 예측 묶음(재작업, 재작업 없음)마다 수와 실제 재작업 비율을 보여 줍니다. 예측은 그 실행이 끝난 뒤에 채점합니다. 아직 열린 단위는 대기로 보여 줍니다. |
| 기준선과 건너뛰기 | 같은 경우에서 정확도에서 다수 결과 비율을 뺀 값을 보여 줍니다. 명시적 건너뛰기를 예측과 건너뛰기 기록 수 대비로 보여 줍니다. |
| 교훈 확인 | 유지나 고쳐 쓰기 답이 있는 제약 수를 `gf learn add`가 그 실행에 기록한 전체 제약 수로 나눕니다. 버린 것은 따로 보여 줍니다. |

관찰은 프로젝트, 실행, 단위, 해당 시도로 맞춥니다. 나중의 재작업과 그 원인에 대한 주장은 분리합니다. 비율에는 분자와 분모를 함께 보여 줍니다. 분모가 비거나 증거가 없으면 "사용할 수 없음"을 보여 줍니다. 범위가 불완전하면 표시하고, 응답 없음과 명시적 건너뛰기를 구분합니다.

승인 시간은 두 기록 사이의 간격일 뿐입니다. 이것으로 주의나 이해를 증명할 수 없습니다.

확인: "재작업 없음" 예측 넷을 기록합니다. 그중 한 단위를 나중에 다시 엽니다. 기준선 대비 개선이 0인지 봅니다. 대기 중인 단위, 건너뛰기 하나, 예측이 없는 이전 실행을 더합니다. 모든 수를 손으로 센 이벤트 이력과 비교합니다.

### CEM-R10 — 확정 전에 분할 비교하기

토론 방식은 2단계나 3단계로 제안된 작업에 적용됩니다. 계획을 나누기 전에 방향 결정이 이미 있으면, 토론 방식은 반드시 그 결정에서 반론을 제시해야 한다(MUST). 그런 결정이 없으면 반론을 계획 승인 때 선택 의견으로 보여도 된다(MAY). 토론을 위해 새 질문을 만들어서는 안 된다(MUST NOT). 대안 분할과 반론은 반드시 다른 모델 계열의 검토자가 내야 한다(MUST). 검토자를 쓸 수 없어도 원래 결정은 반드시 그대로 답할 수 있어야 한다(MUST).

방향 질문에는 구체적인 선택지를 둡니다. 사람이 고르면 고른 선택지와 관련 계획 노드를 기록합니다. 기본이 아닌 선택의 비율과 그 단위의 나중 반려율을 보고합니다. 추적할 수 없는 선택은 두 분모에서 모두 뺍니다.

확인: 검토자의 모델 계열, 선택지, 반론, 계획 버전과의 순서를 확인합니다. 고른 선택과 나중 반려를 선택된 단위와 비교합니다. 방향 결정이 없는 계획을 시험하고 추가 질문이 0개인지 봅니다. 사람 단계나 검토자를 빼고 필수 멈춤 수를 비교합니다.

### CEM-R11 — 실행 규칙과 서명 규칙 지키기

지도 내용은 실행을 승인하거나 게이트 증거를 바꿔서는 안 된다(MUST NOT). 지도는 계획 필드, 실행 노드 종류, 의존 관계를 새로 만들어서는 안 된다(MUST NOT). 지도에서의 상호작용은 반드시 기존 사람 답변 경로와 HMAC v3 형식을 지켜야 한다(MUST). 에이전트는 사람의 답변, 예측, 교훈 확인을 쓰거나 미리 채워서는 안 된다(MUST NOT). 뷰어는 `human.key`를 읽어서는 안 된다(MUST NOT). 뷰어는 답변 검증 결과를 반드시 기존 검증기의 읽기 전용 결과에서만 얻어야 한다(MUST). 검증 결과가 없는 답변은 반드시 검증되지 않은 것으로 다뤄야 한다(MUST).

확인: 승인, 반려, 낡음, 서명 없음 시험 자료를 기존 무결성 검사로 다시 돌립니다. 서명 값, 판정, 범위가 정해진 반려, 준비 상태를 기준과 비교합니다. 답변 기록 하나를 조작합니다. 다른 답변에서는 검증기를 쓸 수 없게 합니다. 조작한 답변은 잘못된 증거로 나오는지 봅니다. 검증 맥락을 쓸 수 없는 답변은 CEM-R14에 따라 `unverifiable here`로 나오는지 봅니다.

### CEM-R12 — 로컬 접근 경계 지키기

지도 접근은 반드시 각 출처의 기존 역할 범위와 프로젝트 범위를 지켜야 한다(MUST). 지도 뷰어는 반드시 Python 표준 라이브러리만 쓰고 루프백 안에 머물러야 한다(MUST).
별도의 원격 화면은 반드시 RA-R3과 RA-R7에 따라서만 지도 결정을 보여 줘야 한다(MUST). [원격 범위](remote-approval.ko.md#ra-r3--원격-읽기와-동작-제한하기)

확인: 역할별 읽기, 다른 프로젝트, 루트 밖 경로, 비밀 키 경로를 시험합니다. 이름, 연결, 개수 어디로도 정보가 새지 않는지 봅니다. import와 네트워크 목적지를 확인합니다.

### CEM-R13 — 모순 드러내기

에이전트는 두 지도 노드 사이에 `conflicts with` 연결을 제안해도 된다(MAY). 제안은 반드시 두 출처 참조를 인용하고 충돌을 한 문장으로 적어야 한다(MUST). 제안은 사람이 확인하기 전까지 반드시 미확인이어야 한다(MUST). 확인된 충돌은 사람이 해결하거나 철회할 때까지 반드시 두 지도 노드 모두에 보여야 한다(MUST).

확인: 서로 어긋나는 생각과 요구를 담은 시험 자료를 씁니다. 연결을 제안하고 두 인용과 미확인 표시를 확인합니다. 확인한 뒤 두 지도 노드의 표시를 봅니다. 해결한 뒤 표시는 사라지고 이력은 남는지 봅니다. [Luhmann](https://zettelkasten.de/communications-with-zettelkastens/) · [ADR 0003](../adr/0003-keep-link-confirmation-with-the-person.md)

### CEM-R14 — 확인된 연결을 검사로 만들기

확인은 원래 키, 실행 기록, 묶인 프로젝트 위치가 있는 사람의 설치본에서만 검증할 수 있습니다.
Git은 선택한 내용과 답변 참조를 담습니다. Git은 다른 곳에서도 쓸 수 있는 증명을 주지 않습니다.

| 항목이나 검사 연결 결과 | `gf map check`가 해야 하는 동작 |
| --- | --- |
| 통과 | 현재 계획의 각 요구에는 반드시 검사로부터 오는 파생 `tests` 연결이나 로컬에서 검증된 `tests` 연결이 있어야 한다(MUST). |
| 실패 | 검사는 반드시 연결되지 않은 요구, 검증된 연결의 사라진 출처, 잘못되었음이 드러난 확인 주장을 이름으로 밝혀야 한다(MUST). |
| 여기서 검증할 수 없음 | 참조된 확인이 검증 맥락 밖에 있으면, 검사는 반드시 `unverifiable here`를 보고하고 영향받는 항목마다 이름을 밝혀야 한다(MUST). |

답변 참조가 없는 주장은 반드시 실패해야 한다(MUST). 자유 질문, 서명된 커밋, 고쳐진 서명, 다른 버전에 대한 답변은 살펴볼 수 있을 때 반드시 실패해야 한다(MUST).
새로 받은 클론, CI, 다른 컴퓨터, 키 고정 변경, 프로젝트 이동에는 원래 검증 맥락이 없을 수 있습니다.
영향받는 항목은 반드시 통과와 실패 밖의 별도 상태로 세어야 한다(MUST). 미확인 제안이 검사 연결을 만들어서는 안 된다(MUST NOT).
검사 연결이 쓸 수 없는 확인 증거에만 의존하면, 그 요구도 반드시 `unverifiable here`로 보여야 한다(MUST).
검사는 그래도 반드시 독립된 실패를 모두 보고해야 한다(MUST).
검사는 반드시 실패가 하나라도 있으면 1, 검증할 수 없는 경우만 있으면 6, 완전히 성공하면 0으로 끝나야 한다(MUST).
검사 결과를 쓰는 쪽은 반드시 종료 코드 6을 성공과도, 실패한 검사와도 구분해야 한다(MUST). 계획은 이 검사를 넣어도 된다(MAY).
지도는 스스로 검사를 더하거나 바꿔서는 안 된다(MUST NOT).

확인: 원래 설치본에서 모든 요구가 연결된 상태를 검사합니다. 0으로 끝나는지 봅니다.
검사 연결을 지우거나, 에이전트 제안만 남기거나, 검증된 연결의 출처를 지웁니다. 영향받는 ID와 함께 1로 끝나는지 봅니다.
서명된 커밋, 조작한 답변, 다른 버전에 대한 유효한 답변을 시도합니다. 종료 코드 1과 해당 ID가 나오는지 봅니다.
원래 키와 기록이 없는 새 클론, CI, 다른 컴퓨터에서 유효한 시험 자료를 반복합니다.
키 고정을 바꾼 뒤와 프로젝트를 옮긴 뒤에도 반복합니다. 6으로 끝나고 영향받는 ID가 모두 나오는지 봅니다. 그 항목이 통과나 실패로 나오지 않는지 봅니다.
독립적으로 연결되지 않은 요구를 더합니다. 1로 끝나고, 그 ID가 나오고, 검증할 수 없는 항목 목록은 그대로인지 봅니다.
[ADR 0017](../adr/0017-confirm-out-of-run-items-in-the-next-run.ko.md) · [ADR 0009](../adr/0009-turn-confirmed-links-into-checks.ko.md) · [Tan 발표 자막(기계 생성)](https://ai.engineer/api/code/reading-download/transcripts/lauren-tan.md)

### CEM-R15 — 용어 후보 제안하기

에이전트는 코드, 명세, 대화에서 도메인 용어 후보를 제안해도 된다(MAY). 후보는 반드시 출처 참조를 인용해야 한다(MUST). 후보는 사람이 확인하거나 정의를 고쳐 쓸 때까지 반드시 미확인이어야 한다(MUST).

확인: 소스 파일 하나에서 후보를 제안합니다. 인용과 미확인 표시를 확인합니다. 사람이 정의를 고쳐 쓰고 새 버전과 작성자를 확인합니다. [ADR 0004](../adr/0004-use-the-domain-glossary-as-an-entry-point.ko.md)

### CEM-R16 — 실행 밖에서 주제 열기

뷰어는 사람이 언제든 토의, 토론, 브레인스토밍 주제를 열 수 있게 해야 한다(MUST). 주제는 반드시 열린 상태의 생각이어야 한다(MUST). 뷰어는 에이전트를 시작하거나 에이전트에게 메시지를 보내서는 안 된다(MUST NOT). 에이전트는 리더 세션에서 동작하지 않는 한 열린 주제를 읽어서는 안 된다(MUST NOT). 작업자 지시서에는 주제 글을 넣어서는 안 된다(MUST NOT). 리더는 반드시 주제 글을 지시가 아닌 인용 자료로 다뤄야 한다(MUST). 리더는 열린 주제마다 제안과 반론으로 답하기를 권장한다(SHOULD). 리더는 반드시 주제의 한 버전에 한 번만 답해야 한다(MUST). 각 답은 사람이 남기기로 할 때까지 반드시 미확인이어야 한다(MUST). 주제는 실행 결정을 만들거나 실행을 멈춰서는 안 된다(MUST NOT).

확인: 실행 없이 주제를 엽니다. 열린 생각이 생기고 에이전트 프로세스가 시작되지 않는지 봅니다. 리더의 답을 더하고 미확인 표시를 봅니다. 지도를 두 번 읽고 답이 하나인지 봅니다. 작업자가 일하는 동안 지시처럼 쓰인 주제를 지도에 넣습니다. 작업자 지시서가 바뀌지 않고 작업자가 아무것도 하지 않는지 봅니다. 실행을 시작하고 필수 답변을 기준과 비교합니다. [ADR 0005](../adr/0005-use-existing-human-slots-for-co-work.ko.md) · [ADR 0007](../adr/0007-show-trails-in-a-separate-local-reader.ko.md)

| R15, R16 | P10. 에이전트의 답과 용어 후보는 제안으로 남습니다. 주제는 실행에 사람 멈춤을 더하지 않습니다. |

승인 요청은 계획 코드와 게이트 코드만 냅니다. 답은 사람만 합니다. 지금의 서명은 답을 질문과 증거에 묶습니다. 서명되지 않은 실행 기록이나 사람의 개인적인 생각 과정은 서명으로 증명되지 않습니다.

같은 계정에서 도는 프로세스는 운영체제 접근 권한을 공유합니다. 에이전트는 사람 역할을 설정하지 않고 사람 답변 명령을 부르지 않습니다. 활동 기록에는 개인 글이 들어가지 않습니다. 새 실행 이벤트가 필요하면 기존 트랜잭션 기록기와 문서화된 이벤트 표를 씁니다. 이 설계는 실행 노드, 필수 답변, 멈춤 상태를 하나도 더하지 않습니다. 반론 기능 시험은 검토 경계를 한 번에 하나만 바꿔 비교합니다. 과제마다 변형별로 두 번 이상 돌립니다. 결과가 뒤집힌 경우, 반복 간 불일치, 걸린 시간, 필수 답변, 선택 대기, 검토 비용을 비교합니다. [Design checklist](../design-sources.md)
