# 원격 승인 화면 (한국어 읽기본)

> 이 문서는 [remote-approval.md](remote-approval.md)의 한국어 읽기본입니다. 기준은 영어 원문입니다.
> 원문 해시: `sha256:0d033e556b66e39a9b505d0c172c841794a930079303f7a44dadb944eedccec5`. 영어 원문이 바뀌면 `scripts/tests/test_reading_copies.py`가 실패합니다.
> 요구 ID와 의무 강도는 원문과 같습니다. 의무 강도는 한국어 표현 뒤에 원문 키워드를 함께 적습니다.

상태: 초안(Draft)

## 목적과 범위

설치본에서 떨어진 곳에 있는 소유자는 등록된 기기에서 대기 중인 질문을 읽고, 그 증거를 살펴보고, 답할 수 있습니다.
설치본 하나는 소유자 한 명을 위해 동작합니다. 팀, 원격 사용자 역할, 여러 사람이 쓰는 계정, 공동 승인, 원격 실행은 범위 밖입니다.
이 설계는 계획 승인, 게이트 질문, 자격이 있는 지도 확인을 다룹니다. 대시보드 전체를 공개하지는 않습니다. [이슈 #4](https://github.com/oozoofrog/graph-flow/issues/4)

## 위협 모델 A

에이전트는 소유자의 운영체제 계정을 함께 쓰고 에이전트 규칙을 따릅니다. 에이전트는 실수하거나 주입된 지시를 받을 수 있습니다.
에이전트는 지원되는 에이전트 인터페이스로 답하거나, 기기를 등록하거나, 기기의 권한을 회수하거나, 접근을 복구할 수 없습니다.
로컬 소유자 절차는 로컬 서명기와 같은 사람 터미널 규칙을 믿습니다.
그 계정에서 도는 적대적인 프로세스는 `human.key`를 읽거나, 등록부를 고치거나, 검증기를 바꿔치기할 수 있습니다.
그런 프로세스는 로컬 서명 정책과 원격 검증을 모두 우회할 수 있습니다.
서명기와 등록을 별도 운영체제 주체로 격리하는 일은 이 설계 밖의 향후 과제입니다. [사람 신원](../../skills/graph-flow/SKILL.md#human-identity)

## 용어

| 용어 | 뜻 |
| --- | --- |
| 소유자 (Owner) | graph-flow 설치본 하나를 관리하고 그 설치본의 질문에 답하는 사람입니다. |
| 기기 (Device) | 자기 자격 증명과 회수할 수 있는 식별자를 가진 등록 하나입니다. 기기 이름표는 물리적 하드웨어를 식별하지 않습니다. |
| 소유자 인증 수단 (Owner factor) | 사용자 확인(user verification)을 요구하는 WebAuthn 패스키입니다. |
| 등록 (Enrollment) | 기기 자격 증명을 이 설치본의 소유자와 연결하는 절차입니다. |
| 로컬 소유자 절차 (Local owner ceremony) | `GF_ROLE=human`과 `GF_HUMAN_TERMINAL=1`이 설정된 로컬 TTY에서 소유자가 하는 동작입니다. |
| 원격 화면 (Remote surface) | 자격이 있는 질문을 읽고 답변을 제출하는 전용 HTTPS 인터페이스입니다. |
| 읽기 세션 (Read session) | 서버가 소유자 인증 수단을 검증한 뒤 발급하는, 자격이 있는 질문을 읽기 위한 시간 제한 자격 증명입니다. |
| 표시된 식별 정보 (Displayed identity) | 소유자가 본 결정의 기존 결정 ID, 질문 해시, 산출물 해시입니다. |
| 답변 확인 요청 (Answer challenge) | 표시된 답변 하나에 대해 소유자 인증 수단을 새로 검증하도록 서버가 보내는 일회용 요청입니다. |

## 요구

이 문서의 의무 표현은 BCP 14([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174))를 따릅니다. 원문 키워드를 괄호 안에 함께 적습니다.

| 원문 키워드 | 이 문서의 한국어 표현 |
| --- | --- |
| MUST | 반드시 …해야 한다 |
| MUST NOT | …해서는 안 된다 |
| SHOULD | …하기를 권장한다 |
| MAY | …해도 된다 |

### RA-R1 — 소유자의 사용 동의 요구하기

새로 설치하거나 업그레이드한 설치본은 소유자가 전에 켜 두지 않았다면 반드시 원격 접근이 꺼진 상태로 시작해야 한다(MUST).
원격 접근은 로컬 소유자 절차에서만 켜도 된다(MAY).
일반 대시보드를 시작할 때는 반드시 루프백 바인드, 토큰 범위, Host 검사를 그대로 지켜야 한다(MUST).
원격 모듈은 현재 의존성 규칙에 따라 반드시 Python 표준 라이브러리만 써야 한다(MUST). [ADR 0012](../adr/0012-keep-remote-access-opt-in.ko.md)

확인: 새 설치본, 업그레이드한 설치본, 명시적으로 켠 설치본 시험 자료에서 리스너와 import를 살펴봅니다. 각 시험 자료에서 일반 대시보드를 엽니다. 원격 설정을 한 시험 자료만 외부 요청을 받는지 봅니다.

### RA-R2 — 네트워크 경계 좁히기

원격 화면은 반드시 설정된 HTTPS 오리진 하나와 명시적인 바인드 주소 하나를 써야 한다(MUST).
원격 화면은 와일드카드 바인드, 암호화하지 않은 외부 트래픽, 다른 인터페이스로의 대체를 반드시 거부해야 한다(MUST).
각 요청에는 반드시 설정된 authority와 일치하는 Host가 정확히 하나 있어야 한다(MUST).
원격 변경 요청은 반드시 POST를 쓰고, 설정된 오리진과 일치하는 Origin을 정확히 하나 담아야 한다(MUST).
외부 TLS는 ADR 0016의 보호된 백엔드 조건에서 명시적으로 설정된 프록시만 종료해도 된다(MAY). [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 직접 연결과 프록시 시험 자료를 authority가 일치하는 경우와 충돌하는 경우로 시험합니다. 변경 요청에서 Origin이 없거나, 중복되거나, null이거나, 다른 오리진이면 거부합니다. 평문 연결, 위조한 전달 헤더, 와일드카드 바인드, 없는 인터페이스를 시도합니다. 비공개 응답이나 변경이 일어나지 않는지 봅니다.

### RA-R3 — 원격 읽기와 동작 제한하기

서버는 읽기 세션을 발급하기 전에 반드시 활성 기기에서 온 새 RA-R12 어설션을 검증해야 한다(MUST).
원격 화면은 제목, 개수, 첨부 파일을 포함한 질문 데이터에 반드시 유효한 읽기 세션을 요구해야 한다(MUST).
원격 화면은 반드시 열린 계획 승인, 게이트가 낸 질문, 명시적인 실행 안 지도 확인과 그 질문이 참조하는 증거만 보여 줘야 한다(MUST).
자격 여부는 반드시 출처 기록에서 정해져야 한다(MUST). 자유 질문의 문구가 승인 권한을 주어서는 안 된다(MUST NOT).
원격 화면은 반드시 기존 파일 제한을 적용하고, 자격 증명, 비공개 기록, 관련 없는 증거를 빼야 한다(MUST).
로컬 토큰, 네트워크 소속, 채팅, 프록시 신원은 반드시 원격 읽기 권한이나 답변 권한을 하나도 주지 않아야 한다(MUST).
비공개 응답은 반드시 캐시를 꺼야 한다(MUST). 원격 화면은 반드시 질문 내용을 실행하지 않고 데이터로 보여 줘야 한다(MUST).
원격 화면은 반드시 로컬 대시보드 경로, 키 고정 변경, 관리 동작, 일반 실행 이력, 실행 제어를 빼야 한다(MUST). 원격 관리 동작은 RA-R8의 기기 권한 회수 하나뿐입니다. [ADR 0012](../adr/0012-keep-remote-access-opt-in.ko.md)

확인: 익명 읽기, 로컬 토큰 읽기, 등록된 기기의 읽기를 비교합니다. 읽기 세션을 만료시키고 질문 데이터가 나오지 않는지 봅니다. 다른 질문의 파일, 비공개 기록, 등록되지 않은 프로젝트를 요청합니다. 캐시 헤더를 확인하고, 지시처럼 쓰인 글이 동작하지 않는 내용으로 보이는지 봅니다. 원격 리스너에서 로컬 전용 경로를 호출합니다. 정보가 새거나 변경이 일어나지 않는지 봅니다.

### RA-R4 — 로컬 소유자 절차로 등록하기

지원되는 에이전트 인터페이스는 답변, 등록, 권한 회수, 복구를 허가해서는 안 된다(MUST NOT).
첫 등록, 추가 등록, 교체, 복구는 반드시 로컬 소유자 절차로 시작해야 한다(MUST).
이 절차는 관리자 권한 없이 반드시 모든 운영체제에서 동작해야 한다(MUST).
이 절차는 반드시 예측할 수 없고, 한 번만 쓸 수 있고, 5분 안에 만료되는 등록 코드를 발급해야 한다(MUST).
서버는 반드시 그 코드를 설치본 하나, 작업 하나, 등록 요청 하나에 묶어야 한다(MUST).
코드를 사용할 때 서버는 반드시 코드 소비와, 그 요청을 후보 세션 하나에 묶는 일을 원자적으로 함께 처리해야 한다(MUST).
후보 기기는 반드시 새 패스키를 등록하고, RA-R12에 따른 새 WebAuthn 어설션으로 그 패스키를 가지고 있음을 증명해야 한다(MUST).
로컬 소유자 절차는 활성화 전에 반드시 소유자가 양쪽 화면의 자격 증명 지문을 비교하고 일치를 승인하게 해야 한다(MUST).
요청은 반드시 코드와 함께 만료되어야 한다(MUST). 서버는 활성화 전에 반드시 만료, 재사용, 자격 증명 바꿔치기를 거부해야 한다(MUST).
등록부가 없거나 비어 있다는 사실이 등록 권한을 주어서는 안 된다(MUST NOT). [ADR 0015](../adr/0015-enroll-through-the-local-owner-ceremony.ko.md)

확인: 지원하는 각 운영체제에서 일반 사용자로 첫 등록과 복구를 해 봅니다. 터미널 조건을 하나씩 빼 봅니다.
지시처럼 쓰인 입력을 포함해, 지원되는 에이전트 인터페이스로 네 작업을 모두 요청합니다. 거부되는지 봅니다.
로컬 토큰만 있는 상태, 등록부가 비었거나 없는 상태에서 등록을 시도합니다. 거부되는지 봅니다.
코드 하나를 동시에 두 번 사용합니다. 후보 세션이 하나만 생기는지 봅니다. 만료 시각에 코드를 사용해 봅니다. 제때 코드를 사용한 뒤 만료 시각에 활성화도 해 봅니다. 둘 다 실패하는지 봅니다.
공개 키를 바꿔치기하거나, 소유 증명이나 로컬 승인을 빼 봅니다. 활성 기기가 생기지 않는지 봅니다.
새 코드로 절차를 끝냅니다. 승인한 자격 증명만 활성화되는지 봅니다.

### RA-R5 — 답변마다 인증하기

각 답변 확인 요청에는 반드시 예측할 수 없는 서버 논스가 들어 있고, 등록이나 읽기 세션 생성과 다른 용도가 지정되어야 한다(MUST).
소유자가 답변을 확정한 뒤, 서버는 반드시 RA-R12에 따라 사용자 확인이 포함된 새 WebAuthn 어설션을 검증해야 한다(MUST).
답변 확인 요청은 반드시 설치본, 기기, 읽기 세션, 프로젝트, 실행, 표시된 식별 정보, 결과, 정확한 답변 글을 묶어야 한다(MUST).
서버는 반드시 유한한 만료 시간을 적용하고, 동시 요청 사이에서도 성공한 증명을 한 번만 소비해야 한다(MUST).
읽기 세션이 만료되면 반드시 그 세션의 답변 확인 요청도 무효가 되어야 한다(MUST).
서버는 반드시 세션 자격 증명과 소유자 인증 수단의 증명을 URL, 로그, 실행 이벤트에 넣지 않아야 한다(MUST).
읽기 세션이나 이전 답변 증명이 다른 답변을 허가해서는 안 된다(MUST NOT). [ADR 0014](../adr/0014-verify-before-signing.ko.md)

확인: 묶인 필드를 하나씩 바꿉니다. 사용자 확인 플래그를 지우고 거부되는지 봅니다. 시험 시계를 만료 시각 너머로 옮깁니다. 같은 제출을 동시에 보내고, 증명을 다른 확인 요청에 다시 씁니다. 원래의 유효한 제출 하나만 받아들여지는지 봅니다.

### RA-R6 — 실행 답변 계약 지키기

서명 직전에 서버는 반드시 기기 권한을 다시 확인하고, 표시된 식별 정보를 기존 트랜잭션 답변 경로에 넘겨야 한다(MUST).
그 경로는 반드시 기존 규칙에 따라 낡은 결정, 대체된 결정, 옛 형식 결정, 옮겨진 결정, 바뀐 결정, 이미 답한 결정, 키가 맞지 않는 결정을 거부해야 한다(MUST).
서명 입력이 같으면 원격 답변과 로컬 대시보드 답변은 반드시 같은 HMAC v3 바이트를 만들어야 한다(MUST).
구속력 있는 실행 승인은 계획 코드와 게이트 코드만 내도 된다(MAY). 답변이 작업을 실행하거나 판정을 내려서는 안 된다(MUST NOT). [ADR 0014](../adr/0014-verify-before-signing.ko.md)

확인: 고정 키 서명 벡터와 검증기 결과를 비교합니다. 표시와 제출 사이에 증거를 바꿉니다. 로컬 답변과 원격 답변을 동시에 보냅니다. 각 거부 시험 자료, 이벤트 수, 이후 게이트 결과를 로컬 기준과 비교합니다.

### RA-R7 — 지도 확인 권한 제한하기

실행 밖에서 고른 항목은 반드시 정확한 항목 버전으로 `pending confirmation` 대기열에 들어가야 한다(MUST).
다음 실행의 계획 승인이나 실행 종료 때, 리더는 반드시 대기 중인 버전을 선택 사항인 자유 질문 하나로 보여 줘야 한다(MUST).
그 질문은 반드시 각 버전을 밝히고 항목마다 따로 선택지를 주어야 한다(MUST).
소유자는 반드시 로컬에서나 원격 화면에서 답할 수 있어야 한다(MUST).
정확한 버전을 명시적으로 고른 검증된 실행 안 답변만 그 항목을 확인해도 된다(MAY).
질문을 건너뛰어도 반드시 필수 답변, 대기, 멈춤 상태가 하나도 늘지 않아야 한다(MUST).
지도는 반드시 일반 계획 승인과 서명된 Git 커밋을 확인 증거로 받아들이지 않고 거부해야 한다(MUST). [ADR 0017](../adr/0017-confirm-out-of-run-items-in-the-next-run.ko.md)

확인: 실행 밖에서 두 버전을 대기열에 넣습니다. 다음 실행 전까지 대기 상태이고 결정이 생기지 않는지 봅니다.
계획 승인과 실행 종료에서, 로컬과 원격으로 반복합니다. 한 항목을 확인하고 다른 항목은 대기 상태로 둡니다.
확인된 버전을 바꾸고 새 버전이 미확인으로 남는지 봅니다. 서명된 커밋만으로, 그리고 일반 계획 승인만으로 확인을 시도합니다.
둘 다 항목을 확인하지 않는지 봅니다. 묶음 질문을 건너뛰고, 필수 멈춤과 준비 상태를 빈 대기열일 때와 비교합니다.

### RA-R8 — 기기 귀속 기록과 권한 회수

설치본은 반드시 기기 목록 보기를 로컬 소유자 절차로 제한해야 한다(MUST).
소유자는 반드시 그 절차로 로컬에서 기기의 권한을 회수할 수 있어야 한다(MUST).
소유자는 원격 화면에서 다른 활성 기기로도 기기의 권한을 회수해도 된다(MAY).
원격 권한 회수는 반드시 그 회수에 묶인 새 RA-R12 어설션을 요구해야 한다(MUST).
원격 화면은 기기를 등록하거나, 복구하거나, 다시 활성화해서는 안 된다(MUST NOT).
등록은 반드시 정확히 한 설치본에 속해야 한다(MUST). 회수된 식별자를 다시 써서는 안 된다(MUST NOT).
권한 회수가 커밋된 뒤, 서버는 반드시 그 기기의 읽기, 아직 남은 확인 요청, 새 답변을 거부해야 한다(MUST).
받아들인 원격 답변마다 반드시 커밋된 답변에 연결된 오래 남는 귀속 기록이 정확히 하나 있어야 한다(MUST).
중단 뒤 복구할 때는 반드시 이 관계를 지키고, 로컬 답변을 원격 기기의 답변으로 기록하지 않아야 한다(MUST).
검증기는 답변이 유효한지 판단할 때 반드시 귀속 기록을 무시해야 한다(MUST). [ADR 0013](../adr/0013-attribute-answers-to-device-enrollments.ko.md)

확인: 같은 이름표로 기기 두 대를 등록합니다. 에이전트 인터페이스로, 그리고 읽기 세션만으로 권한 회수를 시도합니다. 거부되는지 봅니다. 첫 기기의 답변이 대기하는 동안, 다른 기기에서 새 어설션으로 첫 기기의 권한을 회수합니다. 대기 중인 답변이 실패하는지 봅니다. 그 권한 회수 어설션을 다시 보내고 거부되는지 봅니다. 원격 화면에서 등록과 재활성화를 시도하고 거부되는지 봅니다. 내구성 경계마다 쓰기를 중단시킵니다. 다시 시작한 뒤 재시도하고, 답변 참조, 기기 ID, 검증 결과를 비교합니다.

### RA-R9 — 원격 인증 시도 제한하기

비용이 큰 인증 작업을 하기 전에, 서버는 반드시 요청 출처별, 알려진 기기별, 설치본 전체에 유한한 한도를 적용해야 한다(MUST).
한도는 반드시 등록 시도, 읽기 세션 생성, 답변 증명을 다뤄야 한다(MUST).
각 한도에는 반드시 유한한 대기 시간이 있어야 하고, 그 대기 시간은 다시 시작해도 유지되며 로컬 답변은 계속 쓸 수 있어야 한다(MUST).
인증되지 않은 실패가 기기 권한을 영구히 회수하거나 기기가 있는지 드러내서는 안 된다(MUST NOT). [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 한도마다 따로 시도 3회 한도와 60초 대기 시간을 설정합니다. 요청 출처와 기기 식별자를 바꿔 가며 시험합니다. 한도마다 잘못된 시도를 세 번 보냅니다. 네 번째 시도가 거부되는지, 다시 시작한 뒤에도 거부되는지 봅니다. 시계를 대기 시간 너머로 옮기고 유효한 증명이 받아들여지는지 봅니다.

### RA-R10 — 닫힌 상태로 실패하고 로컬에서 복구하기

원격 접근을 끄거나 서버를 다시 시작하면 반드시 모든 읽기 세션, 답변 확인 요청, 대기 중인 등록 요청이 무효가 되어야 한다(MUST).
네트워크나 TLS가 실패해도 반드시 로컬 답변은 계속 쓸 수 있어야 하고, 원격 평문은 받아들이지 않아야 한다(MUST).
복구는 반드시 RA-R4의 로컬 소유자 절차를 쓰고, 교체 기기를 활성화하기 전에 잃어버린 기기의 권한을 회수해야 한다(MUST).
복구는 반드시 이전 답변, 키 고정 정보, 기기 이력을 지켜야 한다(MUST).
등록부를 잃은 뒤에는 설치본이 반드시 이전 기기 권한을 모두 무효로 하고, 원격 답변을 받기 전에 로컬 복구를 요구해야 한다(MUST). [ADR 0015](../adr/0015-enroll-through-the-local-owner-ceremony.ko.md) · [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 원격 접근을 껐다가 다시 켭니다. 종류마다 대기 중인 요청을 하나씩 둔 채 다시 시작합니다. 경로를 끊고, 검증하는 클라이언트로 만료된 인증서를 씁니다. 등록부를 지우고 예전 어설션을 시도합니다. 거부되는지 봅니다. 잃어버린 기기를 로컬에서 복구합니다. 이전 답변, 키 고정 정보, 예전 자격 증명의 거부 여부를 비교합니다.

### RA-R11 — 휴대폰에서도 질문 그대로 보여 주기

원격 화면은 반드시 질문, 이유, 결과가 붙은 선택지, 이력, 검증된 사실, 그다음 파일과 자세한 증거를 이 순서로 보여 줘야 한다(MUST).
휴대폰 화면의 컨트롤은 반드시 증거를 숨기지 않으면서 각 선택지와 그 결과에 닿을 수 있게 해야 한다(MUST).
원격 화면은 반드시 기존의 읽기 게이트, 필수 수정 글, 중립적인 선택지를 지켜야 한다(MUST).
소유자 인증 수단을 검증한 뒤의 명시적인 제출만 답변을 기록해도 된다(MAY). [대시보드 질문 화면](../../skills/graph-flow/references/dashboard.md#question-screens-q1q6)

확인: 계획, 보류, 권한 부여, 증거 누락 시험 자료를 CSS 픽셀 320과 390 너비에서 살펴봅니다. 읽는 순서, 스크롤, 포커스, 활성화된 동작을 확인합니다. 증거를 열고, 인증을 취소하고, 뒤로 이동합니다. 답변이 기록되지 않는지 봅니다. 사람이 하는 연습: 휴대폰에서 긴 선택지와 그 결과를 읽습니다.

### RA-R12 — 패스키 프로필 검증하기

프로젝트는 반드시 WebAuthn 검증기를 직접 소유하고 Python 표준 라이브러리만 써야 한다(MUST).
검증기는 반드시 P-256 위의 EC2 공개 키와 SHA-256을 쓰는 ES256(COSE 알고리즘 `-7`)만 받아들여야 한다(MUST).
검증기는 반드시 좌표 길이, 필드 범위, 곡선 위의 점인지 여부, 엄격한 DER 서명 인코딩, ECDSA 스칼라 범위를 검사해야 한다(MUST).
등록과 어설션 모두에서 검증기는 반드시 절차 종류, 새로 발급한 challenge, 정확한 HTTPS 오리진, 신뢰 당사자 ID 해시를 검사해야 한다(MUST).
검증기는 반드시 교차 오리진 절차를 거부하고, 사용자 존재 확인(user presence)과 사용자 확인(user verification)을 모두 요구해야 한다(MUST).
어설션에서 검증기는 반드시 자격 증명 ID가 예상한 등록과 일치하는지 확인해야 한다(MUST).
검증기는 반드시 인증기 데이터 뒤에 원래 클라이언트 데이터 바이트의 SHA-256 다이제스트를 이어 붙인 값에 대해 서명을 검증해야 한다(MUST).
등록은 반드시 증명(attestation) 형식 `none`과 비어 있는 증명 내용(attestation statement)만 받아들여야 한다(MUST).
검증기는 반드시 클라이언트나 인증기 출력에 있는 지원하지 않는 알고리즘, 증명 형식, 검사하지 않는 확장을 모두 거부해야 한다(MUST).
초기 프로필은 반드시 확장을 하나도 요청하지 않고 받아들이지도 않아야 한다(MUST).
검증기는 세션 토큰과 등록 코드를 포함한 비밀 값을 비교할 때 반드시 상수 시간 비교를 써야 한다(MUST).

CBOR 파서는 반드시 이 프로필에 필요한 정해진 길이의 맵, 정수, 바이트 문자열, 텍스트 문자열만 받아들여야 한다(MUST).
파서는 반드시 16 KiB를 넘는 입력, 네 단계를 넘는 컨테이너 중첩, 항목이 16개를 넘는 맵, 4 KiB를 넘는 문자열을 거부해야 한다(MUST).
파서는 반드시 메모리를 할당하기 전에 한도를 적용하고, 중복 키, 잘린 입력, 잘못된 텍스트, 뒤에 남는 바이트를 거부해야 한다(MUST).

확인: 유효한 등록과 어설션 시험 자료를 받아들입니다. 검사하는 값을 하나씩 바꾸고 거부되는지 봅니다.
다른 알고리즘, 곡선, 증명 형식, 클라이언트나 인증기 확장을 시도합니다. 각 경우를 거부합니다.
형식이 `none`이면서 증명 내용이 비어 있지 않은 경우를 시도합니다. 거부되는지 봅니다.
파서 한도마다 경계값과 그보다 1 큰 값을 시험합니다. 잘못된 DER, 잘못된 점, 범위를 벗어난 스칼라를 거부합니다.
모든 비밀 값 비교가 `hmac.compare_digest` 같은 상수 시간 기본 함수를 쓰는지 살펴봅니다. [WebAuthn 절차](https://www.w3.org/TR/webauthn-3/#sctn-rp-operations) · [ADR 0014](../adr/0014-verify-before-signing.ko.md)

### RA-R13 — 릴리스 전에 검증기 자격 확인하기

프로젝트는 반드시 공개된 WebAuthn 등록·어설션 벡터와 Wycheproof P-256/SHA-256 ECDSA 벡터로 검증기를 확인해야 한다(MUST).
시험은 반드시 유효한 경우, 거부해야 하는 경우, 형식이 잘못된 경우를 다뤄야 한다(MUST). 시험은 반드시 벡터 버전과 기대 결과를 기록해야 한다(MUST).
독립된 암호 검토자는 반드시 파싱, 프로토콜 검사, 비밀 값 비교를 포함해 정확한 검증기 버전을 검토해야 한다(MUST).
릴리스는 벡터 결과가 통과하고 독립 검토가 그 버전을 승인할 때까지 반드시 원격 답변을 막아야 한다(MUST). 프로젝트는 검증기 코드가 생기면 공개 이슈로 그 검토를 요청하기를 권장한다(SHOULD). [ADR 0014](../adr/0014-verify-before-signing.ko.md)

확인: 고정한 벡터를 다시 돌리고 각 결과를 프로필의 기대 결과와 비교합니다.
실패한 벡터, 승인 없음, 다른 버전에 대한 승인 상태에서 원격 답변을 켜 봅니다.
릴리스 시험 자료마다 거부되는지 봅니다. 자격을 갖춘 버전에도 명시적인 사용 동의가 여전히 필요한지 확인합니다.

### RA-R14 — 인증서 준비 안내하기

프로젝트는 반드시 원격 화면용 인증서 준비 안내서를 공개해야 한다(MUST).
안내서는 반드시 적어도 사설 네트워크 방법 하나와 공개 도메인 방법 하나를 다뤄야 한다(MUST).
방법마다 안내서는 반드시 설정된 호스트 이름에 대해 브라우저가 믿는 인증서를 얻는 방법을 보여 줘야 한다(MUST).
안내서는 반드시 원격 화면이 그 인증서와 키를 쓰도록 설정하는 방법과 만료일을 확인하는 방법을 보여 줘야 한다(MUST).
안내서는 반드시 휴대폰에서 인증서 경고 없이 오리진이 열리는지 확인하는 방법을 보여 줘야 한다(MUST).
안내서는 반드시 신뢰할 수 있는 루트 인증서가 없으면 일반적인 휴대폰에서 자체 서명 인증서가 동작하지 않는다고 밝혀야 한다(MUST).
릴리스는 이 안내서 없이 원격 답변을 켜서는 안 된다(MUST NOT). [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 깨끗한 시험 환경에서 안내서의 각 방법을 따라 합니다. 휴대폰 브라우저에서 오리진을 열고 인증서 경고가 나오지 않는지 봅니다. 패스키를 등록하고 질문 하나에 답합니다. 자체 서명 인증서로 반복하고 안내서에 적힌 실패가 나오는지 봅니다. 안내서가 없는 릴리스가 원격 답변을 거부하는지 확인합니다.
