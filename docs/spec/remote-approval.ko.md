# 원격 승인 화면 (한국어 읽기본)

> 이 문서는 [remote-approval.md](remote-approval.md)의 한국어 읽기본입니다. 기준은 영어 원문입니다.
> 원문 해시: `sha256:b90c8a22daf46ebcd09ad52a6c4809c188ca703fae8a6597701de52b395d21d0`. 영어 원문이 바뀌면 `scripts/tests/test_reading_copies.py`가 실패합니다.
> 요구 ID와 의무 강도는 원문과 같습니다. 의무 강도는 한국어 표현 뒤에 원문 키워드를 함께 적습니다.

상태: 초안(Draft)

## 목적과 범위

설치본에서 떨어진 곳에 있는 소유자는 등록된 기기에서 대기 중인 질문을 읽고, 그 증거를 살펴보고, 답할 수 있습니다.
설치본 하나는 소유자 한 명을 위해 동작합니다. 팀, 원격 사용자 역할, 여러 사람이 쓰는 계정, 공동 승인, 원격 실행은 범위 밖입니다.
이 설계는 계획 승인, 게이트 질문, 자격이 있는 지도 확인을 다룹니다. 대시보드 전체를 공개하지는 않습니다. [이슈 #4](https://github.com/oozoofrog/graph-flow/issues/4)

## 위협 모델 A

에이전트는 소유자의 운영체제 계정을 함께 쓰고 에이전트 규칙을 따릅니다. 에이전트는 실수하거나 주입된 지시를 받을 수 있습니다.
에이전트는 지원되는 에이전트 인터페이스로 답하거나, 기기를 등록하거나, 기기의 권한을 회수하거나, 접근을 복구할 수 없습니다.
로컬 소유자 절차는 로컬 서명기와 같은 사람 터미널 규칙을 믿습니다.
그 계정에서 도는 적대적인 프로세스는 `human.key`를 읽거나, 등록부를 고치거나, 검증기를 바꿔치기할 수 있습니다.
그런 프로세스는 로컬 서명 정책과 원격 검증을 모두 우회할 수 있습니다.
서명기와 등록을 별도 운영체제 주체로 격리하는 일은 이 설계 밖의 향후 과제입니다. [사람 신원](../../skills/graph-flow/SKILL.md#human-identity)

## 용어

| 용어 | 뜻 |
| --- | --- |
| 소유자 (Owner) | 공진화 지도 명세의 "사람"입니다. 소유자는 설치본 하나를 관리하고 그 설치본의 질문에 답합니다. |
| 기기 (Device) | 자기 자격 증명과 회수할 수 있는 식별자를 가진 등록 하나입니다. 기기 이름표는 물리적 하드웨어를 식별하지 않습니다. |
| 소유자 인증 수단 (Owner factor) | 사용자 확인(user verification)을 요구하는 WebAuthn 패스키입니다. |
| 등록 (Enrollment) | 기기 자격 증명을 이 설치본의 소유자와 연결하는 절차입니다. |
| 로컬 소유자 절차 (Local owner ceremony) | `GF_ROLE=human`과 `GF_HUMAN_TERMINAL=1`이 설정된 로컬 TTY에서 소유자가 하는 동작입니다. |
| 원격 화면 (Remote surface) | HTTPS 인터페이스와 그 인터페이스 전용으로 네트워크를 마주하는 프로세스입니다. `gf serve`와 분리되어 있습니다. |
| 후보 세션 (Candidate session) | 사용된 등록 요청 하나와, 새 자격 증명 하나를 등록하는 브라우저 사이의 임시 연결입니다. 소유자 접근 권한은 주지 않습니다. |
| 읽기 세션 (Read session) | 원격 화면이 소유자 인증 수단을 검증한 뒤 발급하는, 자격이 있는 질문을 읽기 위한 시간 제한 자격 증명입니다. |
| 표시된 식별 정보 (Displayed identity) | 소유자가 본 결정의 기존 결정 ID, 질문 해시, 산출물 해시입니다. |
| 답변 확인 요청 (Answer challenge) | 표시된 답변 하나에 대해 소유자 인증 수단을 새로 검증하도록 서버가 보내는 일회용 요청입니다. |

## 요구

이 문서의 의무 표현은 BCP 14([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174))를 따릅니다. 원문 키워드를 괄호 안에 함께 적습니다.

| 원문 키워드 | 이 문서의 한국어 표현 |
| --- | --- |
| MUST | 반드시 …해야 한다 |
| MUST NOT | …해서는 안 된다 |
| SHOULD | …하기를 권장한다 |
| MAY | …해도 된다 |

### RA-R1 — 소유자의 사용 동의 요구하기

새로 설치하거나 업그레이드한 설치본은 소유자가 전에 켜 두지 않았다면 반드시 원격 접근을 꺼 둔 상태로 유지해야 한다(MUST).
원격 화면은 반드시 `gf serve`와 분리된 프로세스에서 실행되어야 한다(MUST).
설치본은 로컬 소유자 절차 밖에서 원격 화면을 켜거나 설정해서는 안 된다(MUST NOT).
수동 시작과 재시작은 반드시 로컬 소유자 절차 안에서 일어나야 한다(MUST).
재부팅 뒤 사람 없이 시작할 때는 반드시 소유자가 그 절차로 등록한 운영체제 서비스를 써야 한다(MUST).
`gf serve`와 `--open` 경로를 포함해 에이전트가 실행할 수 있는 명령은 원격 화면을 시작하거나, 설정하거나, 다시 시작해서는 안 된다(MUST NOT).
`gf open --stop`은 반드시 로컬 대시보드만 멈춰야 한다(MUST).
로컬 시작은 반드시 루프백 바인드, 토큰 범위, Host 검사를 그대로 지켜야 한다(MUST).
원격 화면은 반드시 POSIX 호스트에서 Python 표준 라이브러리만 써야 한다(MUST).
트랜잭션 저장소가 `fcntl`을 import하므로 Windows에서 직접 호스팅하는 것은 지원하지 않습니다. [저장소](../../skills/graph-flow/scripts/graphflow/store.py) · [ADR 0012](../adr/0012-keep-remote-access-opt-in.ko.md)

확인: 새 설치본, 업그레이드한 설치본, 전에 켜 둔 설치본 시험 자료를 확인합니다. import, 바인드, 프로세스 ID를 살펴봅니다.
원격 프로세스가 실행 중일 때와 멈췄을 때 각각 대시보드 시작, 열기, 멈춤을 해 봅니다.
각 명령 전후로 원격 프로세스의 신원, 설정, 가용성을 비교합니다.
소유자가 등록한 서비스가 있을 때와 없을 때 재부팅을 흉내 냅니다. 서비스가 등록되어 있고 접근이 켜져 있을 때만 사람 없이 시작되는지 봅니다.

### RA-R2 — 네트워크 경계 좁히기

원격 화면은 반드시 설정된 HTTPS 오리진 하나와 명시적인 바인드 주소 하나를 써야 한다(MUST).
원격 화면은 와일드카드 바인드, 암호화하지 않은 외부 트래픽, 다른 인터페이스로의 대체를 반드시 거부해야 한다(MUST).
각 요청에는 반드시 설정된 authority와 일치하는 Host가 정확히 하나 있어야 한다(MUST).
원격 변경 요청은 반드시 POST를 쓰고, 설정된 오리진과 일치하는 Origin을 정확히 하나 담아야 한다(MUST).
소유자가 ADR 0016의 보호된 백엔드를 설정하지 않았다면 프록시가 외부 TLS를 종료해서는 안 된다(MUST NOT).
로컬 대시보드는 반드시 `Forwarded`, `Via`, 또는 `X-Forwarded-`로 시작하는 헤더가 있는 요청을 거부해야 한다(MUST).
로컬 대시보드는 반드시 경로 처리나 토큰 검사보다 먼저 이 헤더를 검사해야 한다(MUST).
헤더 이름은 값이나 출처와 관계없이 반드시 대소문자를 구분하지 않고 비교해야 한다(MUST). [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 직접 연결과 프록시 시험 자료를 authority가 일치하는 경우와 충돌하는 경우로 시험합니다.
변경 요청에서 Origin이 없거나, 중복되거나, null이거나, 다른 오리진인 경우를 시도합니다. 평문 연결, 와일드카드 바인드, 인터페이스 소실을 시험합니다.
유효한 로컬 토큰과 함께 각 전달 헤더를 로컬 읽기 경로와 답변 경로에 보냅니다.
대소문자가 섞인 이름과 빈 값도 넣습니다. 정보가 새거나 변경이 일어나기 전에 거부되는지 봅니다.

### RA-R3 — 원격 읽기와 동작 제한하기

원격 화면은 읽기 세션을 발급하기 전에 반드시 활성 기기에서 온 새 RA-R12 어설션을 요구해야 한다(MUST).
원격 화면은 모든 질문 제목, 개수, 첨부 파일, 기기 목록에 반드시 유효한 읽기 세션을 요구해야 한다(MUST).
원격 화면은 반드시 열린 계획 승인, 게이트가 낸 질문, 도구가 낸 지도 확인과 그 질문이 참조하는 증거만 보여 줘야 한다(MUST).
지도 확인에 대해서는 반드시 결정 기록에 `issuer: map`과 `purpose: map_confirmation`이 모두 있어야 한다(MUST).
자유 질문은 문구, 선택지, 주장된 증거와 관계없이 반드시 자격이 없는 상태로 남아야 한다(MUST).
원격 화면은 반드시 기존 파일 제한을 적용하고, 자격 증명, 비공개 기록, 관련 없는 증거를 빼야 한다(MUST).
로컬 토큰, 네트워크 소속, 채팅, 프록시 신원으로 얻는 원격 권한은 반드시 없어야 한다(MUST).
비공개 응답은 반드시 캐시를 꺼야 한다(MUST). 두 답변 화면은 반드시 질문 내용을 동작하지 않는 데이터로 보여 줘야 한다(MUST).
원격 화면은 반드시 로컬 대시보드 경로, 키 고정 변경, 일반 실행 이력, 실행 제어를 빼야 한다(MUST).
원격 화면은 반드시 기기 관리를 RA-R8의 목록 보기와 권한 회수로 제한해야 한다(MUST).
후보 세션은 반드시 RA-R4가 허가한 등록 교환만 보여 줘야 한다(MUST). [ADR 0012](../adr/0012-keep-remote-access-opt-in.ko.md)

확인: 익명 읽기, 로컬 토큰 읽기, 만료된 세션의 읽기, 등록된 기기의 읽기를 비교합니다.
지도 확인과 같은 글과 증거를 담은 자유 질문을 시도합니다. 기록된 issuer와 purpose를 하나씩 따로 바꿉니다.
관련 없는 파일, 비공개 기록, 등록되지 않은 프로젝트, 로컬 전용 경로를 요청합니다. 정보가 새거나 변경이 일어나지 않는지 봅니다.
캐시 헤더를 확인합니다. 지시처럼 쓰인 증거가 동작하지 않는 내용으로 보이는지 봅니다.

### RA-R4 — 로컬 소유자 절차로 등록하기

에이전트 인터페이스는 답변, 등록, 권한 회수, 복구를 허가해서는 안 된다(MUST NOT).
첫 등록, 추가 등록, 교체, 복구는 반드시 관리자 권한 없이 로컬 소유자 절차에서 시작해야 한다(MUST).
이 절차는 반드시 운영체제 난수 생성기에서 얻은 40비트 이상의 무작위 값을 담은 일회용 등록 코드를 발급해야 한다(MUST).
코드와 요청은 활성화 도중이더라도 반드시 발급 5분 뒤에 만료되어야 한다(MUST).
원격 화면은 반드시 요청을 설치본과 작업에 묶어야 한다(MUST).
코드를 사용할 때는 반드시 등록 코드를 원자적으로 소비하고 그 요청을 후보 세션 하나에 예약해야 한다(MUST).
후보 기기는 반드시 새 패스키를 등록하고, 새 RA-R12 어설션으로 그 패스키를 가지고 있음을 증명해야 한다(MUST).
증명이 끝나면 후보 기기는 반드시 base32 문자 8개 이상으로 된 일회용 역방향 코드를 보여 줘야 한다(MUST).
원격 화면은 반드시 요청마다 256비트 비밀 값을 새로 만들어야 한다(MUST).
원격 화면은 반드시 요청 ID, 증명된 자격 증명 ID, 공개 키에 대한 HMAC-SHA-256으로 역방향 코드를 만들어야 한다(MUST).
원격 화면은 반드시 요청 비밀 값을 이 계산의 키로 쓰고, 입력 필드를 모호하지 않게 인코딩해야 한다(MUST).
역방향 코드는 반드시 키를 쓴 해시 출력을 40비트 이상 담아야 한다(MUST).
터미널은 반드시 코드 사용 시각과 이스케이프 처리한 클라이언트 사용자 에이전트를 참고 정보로 보여 줘야 한다(MUST).
터미널은 반드시 예상 역방향 코드를 보여 주지 않고, 입력하는 글자도 화면에 나타나지 않게 해야 한다(MUST). 소유자는 반드시 후보 기기의 역방향 코드를 그 터미널에 입력해야 한다(MUST).
활성화는 반드시 만료 전에 그 요청, 세션, 자격 증명을 기준으로 코드를 검증해야 한다(MUST).
이 절차는 반드시 코드 사용과 역방향 코드 제출을 하나하나 RA-R9의 설치본 전체 등록 한도에서 차감해야 한다(MUST).
원격 화면은 반드시 만료, 재사용, 자격 증명 바꿔치기를 거부해야 한다(MUST).
등록부가 없거나 비어 있다는 사실이 등록 권한을 주어서는 안 된다(MUST NOT). [ADR 0015](../adr/0015-enroll-through-the-local-owner-ceremony.ko.md)

확인: 지원하는 호스트에서 일반 사용자로 첫 사용, 추가, 교체, 복구를 해 봅니다.
터미널 조건을 하나씩 빼 봅니다. 에이전트 인터페이스, 대시보드 토큰, 빈 등록부로 시도합니다.
코드를 동시에 두 번 사용합니다. 후보 세션이 하나만 생기는지 봅니다. 코드 사용 시점과 활성화 시점의 만료를 시험합니다.
두 화면을 확인합니다. 틀린 코드, 다른 세션의 코드, 바꿔치기한 키, 빠진 증명을 시도합니다.
소유자가 증명된 자격 증명의 올바른 코드를 입력한 뒤에만 활성화되는지 봅니다.
로그와 프로젝트 파일에 두 코드가 남지 않는지 살펴봅니다.

### RA-R5 — 답변마다 인증하기

각 WebAuthn challenge는 반드시 운영체제 난수 생성기에서 얻은 256비트 이상의 무작위 값을 담고 120초 안에 만료되어야 한다(MUST).
각 challenge는 반드시 자기 고유 용도를 묶고, 상위 세션이나 요청의 만료 시각 또는 그 전에 만료되어야 한다(MUST).
소유자가 답변을 확정한 뒤, 원격 화면은 반드시 RA-R12에 따라 사용자 확인이 포함된 새 WebAuthn 어설션을 검증해야 한다(MUST).
답변 확인 요청은 반드시 설치본, 기기, 읽기 세션, 프로젝트, 실행, 표시된 식별 정보, 결과, 정확한 답변 글을 묶어야 한다(MUST).
원격 화면은 반드시 동시 요청 사이에서도 성공한 증명을 한 번만 소비해야 한다(MUST).
읽기 세션은 반드시 사용 중 연장 없이 발급 후 15분 안에 만료되어야 한다(MUST).
세션 토큰과 요청 한도 쿠키는 반드시 운영체제 난수 생성기에서 얻은 256비트 이상의 무작위 값을 담아야 한다(MUST).
비밀 값 조회는 반드시 별도의 설치본 비밀 값을 키로 쓴 SHA-256 다이제스트와 상수 시간 다이제스트 비교를 써야 한다(MUST).
이 조회 규칙은 등록 코드, 역방향 코드, 세션 토큰, challenge 논스, 요청 한도 쿠키에 적용됩니다.
조회 테이블은 평문 값을 보관해서는 안 된다(MUST NOT).
읽기 세션이 만료되면 반드시 그 세션의 답변 확인 요청도 무효가 되어야 한다(MUST).
원격 화면은 반드시 세션 자격 증명과 소유자 인증 수단의 증명을 URL, 로그, 실행 이벤트 밖에 두어야 한다(MUST).
읽기 세션이나 이전 답변 증명이 다른 답변을 허가해서는 안 된다(MUST NOT). [ADR 0014](../adr/0014-verify-before-signing.ko.md)

확인: 묶인 필드를 하나씩 바꿉니다. 사용자 확인 플래그를 지우고 거부되는지 봅니다. 시험 시계를 만료 시각 너머로 옮깁니다. 같은 제출을 동시에 보내고, 증명을 다른 확인 요청에 다시 씁니다. 원래의 유효한 제출 하나만 받아들여지는지 봅니다.

### RA-R6 — 실행 답변 계약 지키기

서명하기 전에 원격 화면은 반드시 표시된 식별 정보를 기존 트랜잭션 답변 경로에 넘겨야 한다(MUST).
원격 화면은 반드시 최종 권한 확인과 답변 커밋을 권한 회수와 직렬화해야 한다(MUST).
그 경로는 반드시 기존 규칙에 따라 낡은 결정, 대체된 결정, 옛 형식 결정, 옮겨진 결정, 바뀐 결정, 이미 답한 결정, 키가 맞지 않는 결정을 거부해야 한다(MUST).
서명 입력이 같으면 원격 답변과 로컬 대시보드 답변은 반드시 같은 HMAC v3 바이트를 만들어야 한다(MUST).
계획 코드나 게이트 코드가 아닌 발행자는 실행 승인을 내서는 안 된다(MUST NOT). 답변이 작업을 실행하거나 판정을 내려서는 안 된다(MUST NOT). [ADR 0014](../adr/0014-verify-before-signing.ko.md)

확인: 고정 키 서명 벡터와 검증기 결과를 비교합니다. 표시와 제출 사이에 증거를 바꿉니다. 로컬 답변과 원격 답변을 동시에 보냅니다. 각 거부 시험 자료, 이벤트 수, 이후 게이트 결과를 로컬 기준과 비교합니다.

### RA-R7 — 지도 확인 권한 제한하기

실행 밖에서 고를 때는 반드시 CEM-R6에 따라 정확한 Git 버전과 SHA-256 내용 해시를 고정해야 한다(MUST).
다음 계획 승인이나 실행 종료 때, 리더는 반드시 대기 중인 묶음에 대해 `gf map present`를 한 번 실행해야 한다(MUST).
이 명령의 입력에는 반드시 리더가 쓴 질문, 이유, 항목 목록, 선택지, 증거, 답변 글이 하나도 없어야 한다(MUST).
Graph-flow는 반드시 소유자의 언어로 된 고정 템플릿을 써서 대기열로 질문을 만들어야 한다(MUST).
Graph-flow는 반드시 고정된 각 파일을 Git에서 그대로 읽고, 각 항목 ID와 내용 해시를 `evidence`에 묶어야 한다(MUST).
결정은 반드시 `issuer: map`과 `purpose: map_confirmation`을 써야 한다(MUST). `gf decide ask`는 반드시 자유 질문 전용으로 남아야 한다(MUST).
두 화면은 반드시 항목마다 확인, 대기 유지, 거절 선택지를 주고, 확인은 선택되지 않은 상태로 시작해야 한다(MUST).
두 화면은 반드시 CEM-R6의 문법에 따라 소유자의 선택으로 정확한 답변 글을 만들어야 한다(MUST).
지도는 반드시 결정과 묶인 버전에 맞는 검증된 실행 안 답변에서 그 형식만 받아들여야 한다(MUST).
현재 바이트가 다르면 각 화면은 반드시 그 항목을 `changed after selection`으로 표시하고 확인을 거부해야 한다(MUST).
답변 경로는 반드시 확인을 받아들이기 전에 현재 바이트를 다시 검사해야 한다(MUST).
거절은 반드시 이력에 남아야 한다(MUST). 실행 종료는 반드시 CEM-R6에 따라, 작업을 막지 않고 답하지 않은 묶음을 대체 처리해야 한다(MUST).
지도 선택이 계획 작업이나 게이트 작업을 허가해서는 안 된다(MUST NOT). [CEM-R6](co-evolution-map.ko.md#cem-r6--함께하는-방식을-기존-사람-단계에-얹기) · [ADR 0017](../adr/0017-confirm-out-of-run-items-in-the-next-run.ko.md)

확인: 각 사람 단계와 각 화면에서 해 봅니다. 같은 대기열에 대해 표시된 바이트, 결정 증거, 정확한 답변을 비교합니다.
리더가 쓴 글, 자유 질문, 일반 승인, 서명된 커밋을 시도합니다. 확인되지 않는지 봅니다.
표시한 뒤 파일 하나를 바꿉니다. 바뀌지 않은 항목을 확인하고, 바뀐 항목은 미확인으로 남는지 확인합니다.
항목 하나를 거절하고 이력을 살펴봅니다. 답하지 않은 묶음을 두 번 종료합니다. 대체 처리가 한 번만 일어나고 열린 결정이 없는지 봅니다.

### RA-R8 — 기기 귀속 기록과 권한 회수

소유자는 반드시 로컬 소유자 절차로 기기 목록을 보고 권한을 회수할 수 있어야 한다(MUST).
사용자 확인을 거친 유효한 읽기 세션은 반드시 권한 회수를 위해 활성 기기 목록을 원격으로 볼 수 있게 해야 한다(MUST).
원격 목록에는 반드시 소유자 이름표, 바뀌지 않는 기기 ID, 마지막 검증 사용 시각만 있어야 한다(MUST).
원격 권한 회수에는 반드시 다른 활성 기기와 새 RA-R12 어설션이 필요해야 한다(MUST).
그 어설션은 반드시 설치본, 동작하는 기기, 읽기 세션, 대상 기기 ID, 권한 회수 용도를 묶어야 한다(MUST).
원격 화면은 등록, 복구, 재활성화를 시작해서는 안 된다(MUST NOT).
각 등록은 반드시 설치본 하나에 속해야 한다(MUST). 회수된 식별자를 다시 써서는 안 된다(MUST NOT).
권한 회수가 커밋되면 원격 화면은 반드시 그 기기의 읽기, 아직 남은 확인 요청, 새 답변을 거부해야 한다(MUST).
받아들인 원격 답변마다 반드시 커밋된 답변에 연결된 오래 남는 귀속 기록이 정확히 하나 있어야 한다(MUST).
중단 뒤 복구는 반드시 로컬 답변을 기기에 귀속하지 않은 채로 그 연결을 지켜야 한다(MUST).
검증기는 답변의 유효성을 확인할 때 반드시 귀속 기록을 무시해야 한다(MUST). [ADR 0013](../adr/0013-attribute-answers-to-device-enrollments.ko.md)

확인: 같은 이름표로 기기 두 대를 등록합니다. 유효한 세션으로 목록 필드를 확인합니다. 세션을 만료시키고 목록이 나오지 않는지 봅니다.
에이전트의 권한 회수, 읽기 세션만으로의 회수, 자기 자신의 회수, 대상을 바꾼 회수를 시도합니다. 거부되는지 봅니다.
한 기기의 답변이 대기하는 동안 다른 기기에서 그 기기의 권한을 회수합니다. 회수가 커밋된 뒤 거부되는지 봅니다. 회수 증명을 다시 보냅니다.
쓰기 경계마다 중단시킵니다. 다시 시작한 뒤 답변 참조, 기기 ID, 검증 결과를 비교합니다.

### RA-R9 — 원격 인증 시도 제한하기

원격 화면은 작업 스레드를 할당하기 전에 반드시 동시 연결을 최대 32개까지만 받아야 한다(MUST).
작업 스레드는 반드시 5초 절대 기한 안에 TLS 핸드셰이크를 해야 한다(MUST).
각 작업 스레드는 반드시 HTTP 헤더를 5초 안에, 본문을 그 뒤 10초 안에 다 읽어야 한다(MUST).
한도를 넘거나 시간이 지난 연결은 반드시 곧바로 닫혀야 한다(MUST). 원격 화면은 반드시 소비되지 않은 challenge를 설치본마다 128개로 제한해야 한다(MUST).
challenge를 발급하거나 증명을 검증하기 전에, 원격 화면은 반드시 고정된 60초 구간마다 아래의 독립된 한도를 적용해야 한다(MUST).

| 트래픽 종류 | 요청 출처 한도 | 기기 한도 | 설치본 한도 |
| --- | ---: | ---: | ---: |
| 익명(등록 포함) | 10 | — | 60 |
| 등록된 기기 쿠키 | 30 | 20 | 120 |
| 터미널 입력을 포함한 모든 등록 코드 시도 | — | — | 두 종류 합쳐 10 |

이 한도는 성공 여부와 관계없이 받아들인 시도의 수를 제한합니다. 원격 화면은 반드시 구간이 끝날 때까지 넘친 시도를 거부해야 한다(MUST).
원격 화면은 반드시 검증된 등록이나 인증된 로그인 뒤에 무작위 기기 쿠키를 발급해야 한다(MUST).
세션 쿠키와 요청 한도 쿠키는 반드시 `Secure`, `HttpOnly`, `SameSite=Strict`를 써야 한다(MUST).
활성 기기의 인식된 쿠키는 반드시 등록된 기기 종류를 선택해야 한다(MUST).
그 쿠키로 얻는 읽기, 답변, 등록 권한은 반드시 없어야 한다(MUST).
쿠키가 없거나, 알 수 없거나, 회수된 경우에는 반드시 익명 종류를 써야 한다(MUST). 주장된 기기 ID로 한도를 선택해서는 안 된다(MUST NOT).
한 종류의 한도를 다 써도 다른 종류의 한도를 소비해서는 안 된다(MUST NOT).
원격 화면은 반드시 다시 시작해도 카운터와 구간 마감 시각을 유지해야 한다(MUST). 거부된 시도가 구간을 늘려서는 안 된다(MUST NOT).
한도는 반드시 등록, 읽기 세션, 답변, 권한 회수를 다뤄야 한다(MUST). 로컬 답변은 반드시 계속 쓸 수 있어야 한다(MUST).
인증되지 않은 응답이 기기가 있는지 드러내거나 기기 권한을 영구히 회수해서는 안 된다(MUST NOT). [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 멈춘 핸드셰이크와 일부만 보낸 헤더로 모든 연결 자리를 채웁니다. 기한, 작업 스레드 수, 로컬 가용성을 확인합니다.
여러 요청 출처에서 익명 한도를 다 씁니다. 같은 출처에서 유효한 쿠키를 쓰고 검증된 로그인을 끝냅니다.
쿠키만으로, 그리고 추측한 기기 ID로 시도합니다. 권한이 생기지 않는지 봅니다. 각 한도를 한계값과 그보다 하나 많은 값에서 시험합니다.
여러 출처에서 보낸 틀린 역방향 코드를 셉니다. 대기 시간 중에 다시 시작합니다. 구간 경계에서 재시도합니다.

### RA-R10 — 닫힌 상태로 실패하고 로컬에서 복구하기

원격 접근을 끄거나 원격 화면을 다시 시작하면 반드시 모든 읽기 세션, 답변 확인 요청, 대기 중인 등록 요청이 무효가 되어야 한다(MUST).
네트워크나 TLS가 실패해도 반드시 로컬 답변은 계속 쓸 수 있어야 하고, 원격 평문은 거부해야 한다(MUST).
복구는 반드시 RA-R4의 로컬 소유자 절차를 쓰고, 교체 기기를 활성화하기 전에 잃어버린 기기의 권한을 회수해야 한다(MUST).
복구는 반드시 이전 답변, 키 고정 정보, 기기 이력을 지켜야 한다(MUST).
등록부를 잃은 뒤에는 설치본이 반드시 이전 기기 권한을 모두 무효로 하고, 원격 답변을 받기 전에 로컬 복구를 요구해야 한다(MUST).
설치본 신원을 유지하려면, 복구는 반드시 다른 등록을 받기 전에 자격 증명 ID 이력을 되살려야 한다(MUST). [ADR 0015](../adr/0015-enroll-through-the-local-owner-ceremony.ko.md) · [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 원격 접근을 껐다가 다시 켭니다. 종류마다 대기 중인 요청을 하나씩 둔 채 다시 시작합니다. 경로를 끊고, 검증하는 클라이언트로 만료된 인증서를 씁니다. 등록부를 지우고 예전 어설션을 시도합니다. 거부되는지 봅니다. 잃어버린 기기를 로컬에서 복구합니다. 이전 답변, 키 고정 정보, 예전 자격 증명의 거부 여부를 비교합니다.

### RA-R11 — 휴대폰에서도 질문 그대로 보여 주기

원격 화면은 반드시 질문, 이유, 결과가 붙은 선택지, 이력, 검증된 사실, 그다음 파일과 자세한 증거를 이 순서로 보여 줘야 한다(MUST).
휴대폰 화면의 컨트롤은 반드시 증거를 숨기지 않으면서 각 선택지와 그 결과에 닿을 수 있게 해야 한다(MUST).
원격 화면은 반드시 기존의 읽기 게이트, 필수 수정 글, 중립적인 선택지를 지켜야 한다(MUST).
소유자가 소유자 인증 수단을 새로 검증해 명시적으로 제출하지 않았다면 원격 화면은 답변을 기록해서는 안 된다(MUST NOT). [대시보드 질문 화면](../../skills/graph-flow/references/dashboard.md#question-screens-q1q6)

확인: 계획, 보류, 권한 부여, 증거 누락 시험 자료를 CSS 픽셀 320과 390 너비에서 살펴봅니다. 읽는 순서, 스크롤, 포커스, 활성화된 동작을 확인합니다. 증거를 열고, 인증을 취소하고, 뒤로 이동합니다. 답변이 기록되지 않는지 봅니다. 사람이 참여하는 시험에서 휴대폰으로 긴 선택지와 그 결과를 읽습니다.

### RA-R12 — 패스키 프로필 검증하기

프로젝트는 반드시 WebAuthn 검증기를 직접 소유하고 Python 표준 라이브러리만 써야 한다(MUST).
설정된 신뢰 당사자 ID는 반드시 HTTPS 오리진의 DNS 호스트 이름에서 포트를 뺀 값과 같아야 한다(MUST).
설정은 반드시 IP 리터럴을 거부해야 한다(MUST). 원격 페이지는 반드시 `Content-Security-Policy: frame-ancestors 'none'`과 `X-Frame-Options: DENY`를 보내야 한다(MUST).
등록은 반드시 `residentKey: "required"`와 `attestation: "none"`을 요청해야 한다(MUST).
모든 어설션은 반드시 빈 `allowCredentials` 목록을 써야 한다(MUST). 옵션이 등록된 자격 증명 ID를 드러내서는 안 된다(MUST NOT).
두 절차 모두 반드시 `userVerification: "required"`를 요청해야 한다(MUST).
어설션마다 검증기는 반드시 돌려받은 사용자 핸들이 그 설치본에 저장된 소유자 핸들과 일치하는지 확인해야 한다(MUST).
검증기는 반드시 자격 증명 ID가 그 소유자, 그리고 작업에 필요한 등록과 일치하는지 확인해야 한다(MUST).
소유 증명은 반드시 그 후보 세션에 예약된 자격 증명과 일치해야 한다(MUST).
알 수 없는 자격 증명, 회수된 자격 증명, 일치하지 않는 자격 증명은 반드시 같은 공개 거부 응답을 받아야 한다(MUST).

검증기는 반드시 P-256 위의 EC2 공개 키와 SHA-256을 쓰는 ES256(COSE 알고리즘 `-7`)만 받아들여야 한다(MUST).
검증기는 반드시 좌표 길이, 필드 범위, 곡선 위의 점인지 여부, 엄격한 DER 서명 인코딩, ECDSA 스칼라 범위를 검사해야 한다(MUST).
두 절차 모두 반드시 type, 새 challenge, 정확한 HTTPS 오리진, 신뢰 당사자 ID 해시, 사용자 존재 확인, 사용자 확인을 검사해야 한다(MUST).
검증기는 반드시 `crossOrigin: true`와, `topOrigin`이 나타나는 모든 경우를 거부해야 한다(MUST).
등록은 반드시 `fmt: none`, 비어 있는 증명 내용(attestation statement), 바깥 자격 증명 ID와 증명된 자격 증명 ID의 일치를 요구해야 한다(MUST).
자격 증명 ID는 반드시 1–1023바이트여야 한다(MUST). 등록은 반드시 설치본 안의 대기, 활성, 회수 자격 증명 전체에서 유일성을 지켜야 한다(MUST).
검증기는 반드시 각 어설션 서명을, 인증기 데이터 뒤에 원래 클라이언트 데이터 바이트의 SHA-256을 이어 붙인 값에 대해 검증해야 한다(MUST).

두 절차 모두 반드시 백업 가능(BE) 없이 백업 상태(BS)가 설정된 경우를 거부해야 한다(MUST).
등록은 반드시 BE, BS, 서명 카운터를 저장해야 한다(MUST). 어설션은 반드시 BE의 변경을 거부해야 한다(MUST).
두 카운터가 모두 0이 아니면, 검증기는 반드시 받은 카운터가 저장된 값 이하일 때 거부해야 한다(MUST).
검증기는 반드시 동기화 패스키를 포함해 0인 카운터를 허용해야 한다(MUST). 검증기는 반드시 받아들인 가장 높은 카운터를 보관해야 한다(MUST).
검증기는 반드시 자격 증명마다 카운터 비교와 갱신을 직렬화해야 한다(MUST). 검증기는 반드시 검증에 성공한 뒤에만 BS와 카운터를 갱신해야 한다(MUST).

프로필의 확장 요청 목록은 반드시 비어 있어야 한다(MUST). 검증기는 반드시 비어 있지 않은 클라이언트 확장 출력을 거부해야 한다(MUST).
검증기는 반드시 확장 출력이 없는 경우를 받아들여야 한다(MUST).
요청하지 않은 인증기 출력으로는 반드시 정수 값 1, 2, 3 가운데 하나인 등록 `credProtect`만 받아들여야 한다(MUST).
검증기는 반드시 권한 판단에서 그 값을 무시하고, 요청하지 않은 다른 출력은 모두 거부해야 한다(MUST).
CBOR 파서는 반드시 이 프로필에 필요한 정해진 길이의 맵, 정수, 바이트 문자열, 텍스트 문자열만 받아들여야 한다(MUST).
파서는 반드시 16 KiB를 넘는 입력, 네 단계를 넘는 컨테이너 중첩, 항목이 16개를 넘는 맵, 4 KiB를 넘는 문자열을 거부해야 한다(MUST).
파서는 반드시 메모리를 할당하기 전에 한도를 적용하고, 중복 키, 잘린 입력, 잘못된 텍스트, 뒤에 남는 바이트를 거부해야 한다(MUST).

WebAuthn Level 3는 발견 가능한 자격 증명, 어설션 옵션, 인증기 플래그, 등록 검증과 어설션 검증을 정의합니다. [§5.4.6 상주 키](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#enum-residentKeyRequirement) · [§5.5 어설션 옵션](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#dictionary-assertion-options) · [§6.1 인증기 데이터](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-authenticator-data) · [§7.1 등록](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-registering-a-new-credential) · [§7.2 어설션](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-verifying-assertion)

정확한 호스트 규칙, 카운터 거부, 프레이밍 헤더, 확장 허용 목록은 이 프로젝트의 정책입니다.
CTAP는 `credProtect`의 등록 값을 정의합니다. [CTAP 2.2 §12.1](https://fidoalliance.org/specs/fido-v2.2-ps-20250714/fido-client-to-authenticator-protocol-v2.2-ps-20250714.html)

확인: 옵션과 응답 헤더를 살펴봅니다. 핸들을 빼거나, 바꾸거나, 알 수 없는 ID나 회수된 ID를 씁니다.
공개 상태 코드와 본문을 비교합니다. ID 길이의 양쪽 경계를 확인하고, 중복 등록을 동시에 보냅니다.
카운터가 늘어날 때, 같을 때, 줄어들 때, 0으로 바뀔 때를 시험합니다. BE와 BS를 하나씩 바꿉니다.
`topOrigin`을 넣고, 오리진, 호스트, 플래그 검사를 하나씩 바꿉니다. 모든 암호 경계와 파서 경계를 통과해야 하는 시험 자료와 거부해야 하는 시험 자료로 시험합니다.
잘못된 서명, 잘못된 점, 비어 있지 않은 증명 내용, 지원하지 않는 알고리즘, 허용되지 않는 확장을 거부합니다.
비밀 값 비교가 `hmac.compare_digest` 같은 상수 시간 기본 함수를 쓰는지 살펴봅니다. [ADR 0014](../adr/0014-verify-before-signing.ko.md)

### RA-R13 — 릴리스 전에 검증기 자격 확인하기

프로젝트는 반드시 공개된 WebAuthn 등록·어설션 벡터와 Wycheproof P-256/SHA-256 ECDSA 벡터로 검증기를 확인해야 한다(MUST).
릴리스 자격 확인은 반드시 플랫폼 인증기와 로밍 인증기에서 얻은 실제 기기의 등록·어설션 시험 자료를 다시 돌려야 한다(MUST).
이 시험 자료는 반드시 확장 출력이 없는 경우와, 실제 기기가 요청 없이 보낸 등록 `credProtect`를 다뤄야 한다(MUST).
프로젝트는 반드시 수집한 자료마다 브라우저, 운영체제, 인증기, 관찰된 출력, 기대 결과를 기록해야 한다(MUST).
시험 자료는 반드시 유효한 경우, 거부해야 하는 경우, 형식이 잘못된 경우를 다뤄야 한다(MUST). 시험 자료는 반드시 벡터 버전과 기대 결과를 기록해야 한다(MUST).
독립된 암호 검토자는 반드시 파싱, 프로토콜 검사, 비밀 값 비교를 포함해 정확한 검증기 버전을 검토해야 한다(MUST).
릴리스는 벡터와 실제 기기 시험 자료가 통과하고 독립 검토가 그 버전을 승인할 때까지 반드시 원격 답변을 막아야 한다(MUST). 프로젝트는 검증기 코드가 생기면 공개 이슈로 그 검토를 요청하기를 권장한다(SHOULD). [ADR 0014](../adr/0014-verify-before-signing.ko.md)

확인: 고정한 벡터를 다시 돌리고 각 결과를 프로필의 기대 결과와 비교합니다.
실패한 벡터, 승인 없음, 다른 버전에 대한 승인 상태에서 원격 답변을 켜 봅니다.
릴리스 시험 자료마다 거부되는지 봅니다. 자격을 갖춘 버전에도 명시적인 사용 동의가 여전히 필요한지 확인합니다.
[공개 WebAuthn 시험 자료](https://github.com/Yubico/java-webauthn-server/blob/main/webauthn-server-core/src/test/scala/com/yubico/webauthn/RegistrationTestData.scala) · [Wycheproof DER 벡터](https://github.com/C2SP/wycheproof/blob/main/testvectors_v1/ecdsa_secp256r1_sha256_test.json)

### RA-R14 — 인증서 준비 안내하기

프로젝트는 반드시 원격 화면용 인증서 준비 안내서를 공개해야 한다(MUST).
안내서는 반드시 사설 네트워크 방법과 공개 도메인 방법을 각각 하나 이상 다뤄야 한다(MUST).
방법마다 안내서는 반드시 설정된 호스트 이름에 대해 브라우저가 믿는 인증서를 얻는 방법을 보여 줘야 한다(MUST).
안내서는 반드시 원격 화면이 그 인증서와 키를 쓰도록 설정하는 방법과 만료일을 확인하는 방법을 보여 줘야 한다(MUST).
안내서는 반드시 휴대폰에서 인증서 경고 없이 오리진이 열리는지 확인하는 방법을 보여 줘야 한다(MUST).
안내서는 반드시 신뢰할 수 있는 루트 인증서가 없으면 일반적인 휴대폰에서 자체 서명 인증서가 동작하지 않는다고 밝혀야 한다(MUST).
직접 TLS에서 원격 화면은 반드시 원자적 교체를 포함해 인증서 파일이나 키 파일의 변경을 60초 안에 감지해야 한다(MUST).
원격 화면은 반드시 프로세스를 다시 시작하지 않고, 서로 맞는 유효한 쌍을 새 핸드셰이크용으로 원자적으로 불러와야 한다(MUST).
다시 불러오기에 실패하면 원격 화면은 반드시 로컬에 오류를 알려야 한다(MUST). 원격 화면은 반드시 이전 쌍이 유효한 동안 그 쌍을 유지해야 한다(MUST).
유효한 쌍이 남아 있지 않으면 원격 화면은 반드시 새 핸드셰이크를 멈춰야 한다(MUST).
인증서 만료 30일 전부터 `gf status`와 로컬 대시보드는 반드시 호스트 이름과 만료 시각을 담아 경고해야 한다(MUST).
원격 화면이 연결을 받지 않게 되어도, 두 로컬 보기는 반드시 만료와 다시 불러오기 실패를 알려야 한다(MUST).
프록시 방식에서는 프록시가 반드시 바뀐 외부 인증서 파일을 다시 불러와야 한다(MUST). 두 로컬 보기는 반드시 만료를 알릴 때 프록시에 설정된 공개 인증서 파일을 써야 한다(MUST).
릴리스는 이 안내서 없이 원격 답변을 켜서는 안 된다(MUST NOT). [ADR 0016](../adr/0016-assign-tls-responsibility.ko.md)

확인: 깨끗한 시험 환경에서 안내서의 각 방법을 따라 합니다. 휴대폰 브라우저에서 오리진을 열고 인증서 경고가 나오지 않는지 봅니다. 패스키를 등록하고 질문 하나에 답합니다. 자체 서명 인증서로 반복하고 안내서에 적힌 실패가 나오는지 봅니다. 안내서가 없는 릴리스가 원격 답변을 거부하는지 확인합니다.
서비스 중에 인증서와 키를 바꿉니다. 새 연결에서 인증서를 살펴보고 프로세스 ID를 비교합니다.
맞지 않는 쌍으로 바꾸는 경우와 이전 쌍이 만료되는 경우를 시험합니다. 30일 경계에서 두 로컬 보기를 확인합니다. 프록시 방식에서는 제공되는 인증서와 설정된 공개 파일을 비교합니다.

| RA-R7, RA-R11 | P10. 결정이나 승인만 소유자에게 갑니다. 원격 인증은 실행 질문이나 필수 멈춤을 더하지 않습니다. |

에이전트는 `GF_HOME`을 바꾸거나 `GF_ROLE=human`이나 `GF_HUMAN_TERMINAL`을 설정하지 않습니다. `gf decide answer`를 실행하거나 두 대시보드 API 가운데 어느 것도 쓰지 않습니다.
에이전트는 `human.key`를 다루거나, `server.json`을 읽거나, 실행 파일을 직접 고치지 않습니다.
에이전트는 원격 화면을 시작하거나, 설정하거나, 다시 시작하지 않습니다. 기기를 등록하거나, 기기의 권한을 회수하거나, 접근을 복구하지 않습니다.
에이전트는 등록 코드, 역방향 코드, 절차 출력을 읽거나, 전달하거나, 사용하지 않습니다. [사람 신원](../../skills/graph-flow/SKILL.md#human-identity) · [원칙](../../skills/graph-flow/references/principles.md) · [리더](../../skills/graph-flow/references/leader.md)

이 설계는 위협 모델 A에서 소유자 기기, 검증기, 로컬 소유자 절차를 믿습니다.
패스키는 challenge를 인증합니다. 소유자는 무엇에 서명할지 고를 때 화면에 표시된 질문과 답변 글에 의지합니다.
공개적으로 노출되면 서비스가 동작한다는 사실이 드러나거나 처리 용량이 바닥날 수 있습니다. 권한 회수는 이미 보여 준 증거를 되돌리지 못합니다.

## 구현 의무

[ADR 0011](../adr/0011-code-follows-the-spec.ko.md)에 따라 아래 변경을 구현과 함께 전달합니다.

- `records.md`의 네트워크 규칙과 답변 권한 규칙을 고칩니다. 로컬 소유자 경로와 검증된 원격 소유자 경로를 문서화합니다.
  지도 발행자, 정규 답변, 대체 이벤트, 서명되지 않은 귀속 기록을 기록합니다. [기록](../../skills/graph-flow/references/records.md)
- `principles.md`의 고정된 서명 메모를 고칩니다. 네트워크를 마주하는 새 진입점이 바뀌지 않은 서명기를 부릅니다.
  이제 네트워크를 마주하는 프로세스가 `human.key`를 다룹니다. 그에 따른 노출을 위협 모델 A 아래에 문서화합니다. [원칙](../../skills/graph-flow/references/principles.md)
- 위의 에이전트 금지 사항을 `SKILL.md`와 `leader.md`에 더합니다. 두 코드와 모든 절차 출력을 포함합니다.
  리더의 단일 제시 명령과, 그 명령에 작성 입력이 없다는 점을 문서화합니다. [스킬](../../skills/graph-flow/SKILL.md#human-identity) · [리더](../../skills/graph-flow/references/leader.md)
- 시험 하네스는 graph-flow를 import하거나 자식 프로세스를 띄우기 전에 반드시 일회용 설치본, 운영체제 홈, 프로젝트, 격리된 `GF_HOME`을 만들어야 한다(MUST).
  하네스는 반드시 쓰기를 그 안으로 제한하고, 별칭, 상속된 설정, 서비스 등록을 포함해 소유자의 실제 경로를 거부해야 한다(MUST).
  하네스는 반드시 시험용 자격 증명, 루프백 전송, 서비스 대역을 써야 한다(MUST).
  에이전트는 자기 설치본 설정을 덮어쓰지 않고 절차 출력도 받지 않은 채 이 하네스를 실행합니다.
  안전하지 않은 경로가 초기화 전에 중단되는지 확인합니다. 보호된 감시용 설치본으로 어떤 시험도 외부 설정이나 등록부에 닿지 않는지 확인합니다.
