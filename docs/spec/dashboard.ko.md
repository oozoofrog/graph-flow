## 목적과 범위

설치 소유자는 특정 요청에 답하려고 실행을 엽니다. 소유자는 첫 화면에서 그 요청을 찾고, 답의 결과를 이해하고, 어느 동작이 서명인지 알아봅니다. 진행 화면은 작업마다 누가 일하고 있는지 보여 줍니다. 소유자는 기록 화면에서 실패를 그 실패가 나온 시도까지 거슬러 찾습니다. [대시보드 재설계](https://github.com/oozoofrog/graph-flow/issues/11) · [수정판 승인](https://github.com/oozoofrog/graph-flow/issues/10)

이 설계는 로컬 대시보드와, 구조 수정에 적용하는 계획 계약을 다룹니다. 휴대전화 배치와 원격 접근은 이슈 #4에서 다룹니다. 카드의 읽기 순서, 근거 링크, 답 이름은 그래프 좌표, 마우스 올리기(hover), 입력 장치와 관계없이 작동합니다. 그래서 이후 휴대전화 배치에 이 요소를 그대로 옮겨 쓸 수 있습니다. 이 설계는 원격 엔드포인트나, 사람이 멈춰서 응답하는 새 단계를 만들지 않습니다. [원격 승인](remote-approval.ko.md) · [이슈 #4](https://github.com/oozoofrog/graph-flow/issues/4)

## 용어

| 용어 | 원문 | 이 문서에서의 뜻 |
| --- | --- | --- |
| 소유자 | Owner | 이 설치를 관리하고, 그 답에 서명할 권한이 있는 사람. |
| 리더 | Leader | 계획을 게시하고 `gf gate`를 실행하는 행위자. |
| 요청한 쪽 | Requester | 이 요청을 시작한 행위자. 리더, 작업자, 검토자, 소유자 중 누구든 요청한 쪽이 됩니다. |
| 발행 주체 | Issuer | 구속력 있는 결정을 낸 것으로 기록된 프로그램 구성 요소. 계획이나 게이트가 그 예입니다. |
| 작업 | Task | 계획의 노드 하나. work 노드, review 노드, decision 노드를 모두 포함합니다. |
| 카드 | Card | 내 차례에서 지금 할 일 하나나, 복구가 필요한 요청 하나를 보여 주는 항목. |
| 대기 항목 | Waiting item | 소유자가 지금 처리할 수 있는 일. 키 복구도 포함합니다. 답변 대기 건수에는 소유자가 답할 수 있는 결정만 들어갑니다. 예정된 요청과 대체된 요청은 두 건수 어디에도 들어가지 않습니다. |
| 자유 질문 | Free question | 정보나 방향을 묻는 요청. 답은 요청한 쪽에 돌아갑니다. |
| 읽기 조건 | Reading gate | 특정 답 버튼이 활성화되기 전에 소유자가 열어야 하는 자료. |
| 구조 수정 | Structural revision | 기존 계획을 바꾸어, 계획 계약에서 정한 구조 식별값이 달라지는 변경. |
| 수정 노트 | Revision note | 구조 수정 하나에 대해 리더가 네 부분으로 쓴 설명. |
| 위험도 | Risk lane | 작업에 필요한 검사와 승인을 정하는 위험 수준. |

아래 표는 이 읽기본에서 쓰는 번역 용어입니다. 영어 원문에는 없는 읽기 도움 자료이며 효력이 없습니다.

| 한국어 | 원문 |
| --- | --- |
| 내 차례 · 진행 · 그래프 · 기록 화면 | My turn · Progress · Graph · Log |
| 작업자 · 검토자 | worker · reviewer |
| 시도 · 근거 · 근거 상세 | attempt · evidence · evidence disclosure |
| 버튼 · 답 버튼 | control · answer control |
| 서명 · 승인 · 돌려보내기 · 살펴보기 | signing · approve · send back · inspect |
| 수락 · 허가 · 허가 거부 | accept · authorize · refuse permission |
| 반려 | rejection, returned attempt (게이트가 시도를 받아들이지 않은 기록) |
| 수정판 | revision (기록된 계획의 한 판) |
| 소유자 할 일 · 답변 대기 | owner action · pending answer |
| 키 복구 · 요청 복구 | key recovery · repair (리더가 요청을 고치는 일) |
| 기록 | records (실행에 저장된 이벤트 줄) |
| 묶다 | bind (서명이 특정 질문과 근거를 포함하게 하는 일) |

이벤트 행위자에는 이미 역할과 세션이 있습니다. 이슈 #3은 가능할 때 신원 필드(`host`, `host_session`, `session_name`, `agent_kind`, `agent_model`)를 더 제공합니다. 이 이슈의 작업은 지금 멈춰 있습니다. 이 필드가 생기기 전에도 요청한 쪽은 요청을 시작한 이벤트에서 찾습니다. [이슈 #3](https://github.com/oozoofrog/graph-flow/issues/3) · [계획 계약](../../skills/graph-flow/references/plan.md#plan-approval)

## 검증용 픽스처

격리된 기록을 사용합니다. 에이전트는 소유자의 대시보드를 절대 조작하지 않습니다. 구현은 아래 사례와 그 변형을 `dev/screens/`에 추가합니다(DASH-R24). 진단 캡처가 출발점인 A~E 사례를 제공합니다. 호환성 확인을 위해 수정 노트 도입 이전의 B 사본을 보관합니다. C는 진행 중인 작업을 보여 주고, E는 완료된 실행을 보여 줍니다. C와 E에는 대기 항목이 없습니다.

DASH-R1~R3과 DASH-R12~R13의 결정 종류별 확인에는 이 표를 기댓값으로 씁니다. 각 행에서 요청한 쪽, 서명할 질문, 계기, 결과, 선택지, 활성화 조건을 픽스처 기록과 대조합니다. ‘게이트’는 발행 주체를 가리킵니다. 게이트 요청에서는 요청한 쪽과 함께, DASH-R1에 따른 별도의 ‘작업자’ 줄도 확인합니다.

| 입력 | 묻는 쪽과 지금 묻는 이유 | 확인할 결과와 버튼 |
| --- | --- | --- |
| A · 첫 계획 | `plan.set`의 리더. 첫 승인 이유(`planInitialReason`)를 두 언어로 표시합니다. | 새 작업 시작은 대기합니다. 승인은 조건을 갖춘 작업의 시작을 허용합니다. 목록에서 작업을 하나씩 엽니다. |
| B · 수정된 계획과 자유 질문 | 새 `plan.set`의 리더. 이와 별도로, 페이지 크기를 묻는 `decision.ask`의 행위자. | 바뀐 검사는 API 작업에 영향을 줍니다. 답은 요청한 쪽에 돌아갑니다. 제시된 답 하나에 서명하거나 답을 직접 입력합니다. 수정판 읽기 조건은 계획에만 적용합니다. |
| D · `human_check` | 게이트. 제출된 안내서를 처음 읽는 사람이 읽어 봐야 합니다. | 돌려보내면 안내서는 고칠 대상으로 남습니다. `guide.txt`나 근거를 연 뒤에만 수락합니다. |
| F · `hold` | 게이트. 묶인 제출물에서 독립 검토가 실패했습니다. | 수락하면 기록된 실패를 뒤집습니다. 돌려보내면 작업은 막힌 채로 남습니다. 파일만 열면 수락 버튼은 비활성 상태로 남습니다. 근거 상세를 엽니다. |
| G · `lane3` | 게이트. 제출된 작업에 위험도 3 허가가 필요합니다. | 기록된 결과를 허가하거나 돌려보냅니다. 허가하려면 파일이나 근거 상세를 엽니다. |
| H · `trajectory` | 게이트. 수정이나 되돌리기 때문에 검토가 시작되었습니다. 작업은 마지막 시도까지 썼습니다. | 수락은 게이트 평가가 이어지도록 허용합니다. 돌려보내면 다음 시도 전에 계획 수정판이 필요합니다. 기록된 근거를 엽니다. |
| I · 계획된 허가(목적 `node`) | 게이트. 결정 작업이 준비되었습니다. 작성된 질문과 `context.why`를 표시합니다. 작업자의 제출물은 없습니다. | `if_approved`, `if_rejected`, `undo`를 작성된 그대로 표시합니다. 후속 작업은 기록에서 찾아 밝힙니다. 거부하면 후속 작업은 막힌 채로 남습니다. 승인은 게이트가 결정 작업을 통과시키도록 허용합니다. 근거 상세를 엽니다. 거부 메모는 선택 사항입니다. |
| J · 구조 변경 없는 재승인 | `project_moved`, 이전 실행 이어 하기, `replaced_unverifiable`에는 계획을 다시 게시한 리더를 씁니다. `key_repinned`에는 요청을 시작한 `human.repin` 행위자를 씁니다. | 네 변형에서 각각 기록된 이동, 이전 작업, 검증할 수 없는 이전 계획, 키 변경을 표시합니다. 돌려보내면 새 작업 시작은 막힌 채로 남습니다. 승인은 조건을 갖춘 작업이 이어지도록 허용합니다. DASH-R20을 적용합니다. |
| K · 판단할 자료 없음 | 게이트. 검토가 근거 없이 수락을 요청합니다. | ‘판단할 자료가 없어요’(There is nothing here to judge by)라고 표시합니다. 돌려보내기를 먼저 보여 줍니다. 소유자가 근거 없이 수락하겠다고 확인할 때까지 수락은 보조 동작으로 남습니다. |

## 기존 계약에서 바뀌는 점

- DASH-R1, R2, R19는 일반적인 수정판 질문, 그리고 계획 화면이 만드는 제목과 충돌합니다. 묶인 질문과 요청을 시작한 행위자를 씁니다. [계획 발행 주체](../../skills/graph-flow/scripts/graphflow/cli.py#L119) · [질문 렌더러](../../skills/graph-flow/scripts/graphflow/page.js#L1735) · [문구와 이후 질문](../../skills/graph-flow/references/records.md#wording-and-later-questions)
- DASH-R5와 R21은 지금 할 일에 쓰던 기존 받은 요청 목록과 건수 규칙을 대신합니다. 예정된 이후 응답은 지금처럼 따로 셉니다. [대시보드 건수](../../skills/graph-flow/references/dashboard.md#L460)
- DASH-R9와 R19는 계획 게시 입력, 이벤트, 승인 묶음을 넓힙니다. ADR 0020은 실행 필드, 구조 식별값에서 빼는 필드, V1 검사 범위를 정합니다. DASH-R11은 구조 수정을 알릴 때 리더가 쓰던 한 문장 전달을 바꿉니다. [계획 식별값](../../skills/graph-flow/references/plan.md#L124) · [실행 필드](../../skills/graph-flow/references/plan.md#L156) · [리더 지침](../../skills/graph-flow/references/leader.md#L69)

### DASH-R1 — 요청한 쪽과 소유자 밝히기

결정마다 카드는 요청을 시작한 행위자의 역할, 작업(있을 때), 세션으로 요청한 쪽을 반드시 밝혀야 한다(MUST). 계획 승인에서는 해당 `plan.set`의 행위자를, 키 재등록 요청에서는 `human.repin`의 행위자를 반드시 써야 한다(MUST). 게이트 결정에서는 같은 요청 트랜잭션에 있는 해당 `gate.verdict`의 행위자를 반드시 써야 한다(MUST). 자유 질문에서는 `decision.ask`의 행위자를 반드시 써야 한다(MUST). 발행 주체가 기록되어 있으면 카드는 발행 주체를 따로 반드시 밝혀야 한다(MUST). 게이트 카드는 묶인 제출물의 작업자 세션과 배정 기록으로 ‘작업자’(Work by)를 보여 주거나, 해당하는 제출물이 없다고 반드시 밝혀야 한다(MUST). 카드와 기록 화면은 같은 요청한 쪽을 보여 주고, 기록된 에이전트 종류와 모델이 있으면 반드시 함께 보여 줘야 한다(MUST). 빠진 신원 필드마다 반드시 ‘기록되지 않음’(Not recorded)이라는 이름을 써야 한다(MUST). 답하는 사람은 반드시 ‘설치 소유자’(Install owner)라는 역할로 나와야 한다(MUST). 답하는 사람의 표시에 개인 이름, 이메일 주소, 호스트 이름을 드러내서는 안 된다(MUST NOT).

확인: A, B, 그리고 D~K의 결정 사례를 픽스처 표와 대조한다. B의 계획, B의 자유 질문, D의 작업자에 서로 다른 세션을 준다. B의 자유 질문을 작업자가 보내는 경우와 검토자가 보내는 경우로 반복한다. 역할, 작업, 세션을 기록 화면에서 요청을 시작한 이벤트와 맞춰 본다. D의 작업자를 그 제출물과 맞춰 본다. I에서는 ‘제출물 없음’(No submission)이 나온다. 이슈 #3 필드를 지운 다음, 요청을 시작한 세션도 지운다. 빠진 필드에만 빈칸 표시가 나오고, 모든 결정에 ‘설치 소유자’가 나온다.

### DASH-R2 — 질문과 묻는 계기 밝히기

결정 카드마다 선택할 내용을 한 문장으로 밝히고, 답이 묶이는 `decision.ask.question` 원문으로 반드시 시작해야 한다(MUST). 기록된 질문이 한 문장을 넘으면 카드는 그 질문을 원문 그대로 제목으로 두고, 한 문장 설명을 그 아래에 반드시 두어야 한다(MUST). 카드는 기록된 계기로 지금 답해야 하는 이유를 설명하거나, 계기가 없으면 그 사실을 반드시 밝혀야 한다(MUST). 자유 질문은 그 질문이 가진 효력의 설명보다 반드시 먼저 나와야 한다(MUST).

확인: 픽스처 표의 결정 행을 모두 확인한다. 두 언어에서 제목을 묶인 질문과 대조한다. A에는 언어별 `planInitialReason`이 나온다. B에는 반려와 바뀐 API 검사가 나온다. D에는 제출된 안내서를 처음 읽는 사람에 관한 질문이 나온다. B의 페이지 크기 질문은 답의 설명보다 먼저 나온다. J에서는 계획 식별값이 같아도 기록된 재승인 원인을 각각 구분한다.

### DASH-R3 — 답마다 결과 설명하기

카드는 각 답 버튼 옆에, 해당하는 경우 영향을 받는 작업·남는 차단·시도 비용을 포함해 기록에서 계산한 결과를 반드시 보여 줘야 한다(MUST). 자유 질문에서는 답을 받는 쪽을 밝히고, 그 답이 어떤 승인도 주지 않는다는 점을 반드시 밝혀야 한다(MUST). 계획된 결정이나 사람 확인에서는 작성된 맥락 필드(`why`, `if_approved`, `if_rejected`, `undo`) 가운데 값이 있는 것을 모두 작성자 표시 아래에 반드시 보여 줘야 한다(MUST).

확인: 픽스처 표의 결정 행마다 제공되는 버튼과 다음 결과를 대조한다. B에 막힌 작업을 즉시 풀어 준다고 약속하는 수정 노트를 넣는다. 승인과 돌려보내기 옆에는 실제 차단이 나온다. D에서는 돌려보낸 뒤 두 번째 시도가 나온다. 한도에 이른 H에서는 기록된 시도 한도가 나오고, 이 계획으로는 더 시도하지 않는다고 나온다. I의 맥락 필드마다 서로 다른 글을 넣고, 표시된 값을 묶인 근거와 하나씩 대조한다.

### DASH-R4 — 읽을 근거 안내하기

카드마다 소유자가 행동하는 데 필요한 자료가 있으면, 그 이름과 링크를 반드시 보여 줘야 한다(MUST). 카드는 소유자가 읽지 않아도 되는 자료를 반드시 밝혀야 한다(MUST). 꼭 읽을 자료가 없으면 카드는 그 사실을 반드시 밝혀야 한다(MUST).

확인: D에서는 꼭 읽을 자료와 골라 볼 세부 내용이 이름이 다른 DOM 구역으로 나뉘어 있다. 꼭 읽을 구역에는 안내서 링크와 근거 상세 링크가 있고, 둘 중 하나를 열면 된다. B의 자유 질문에는 꼭 읽을 자료가 없다고 나온다. 읽기 링크를 하나씩 따라가도 답 기록은 0개다.

### DASH-R5 — 내 차례로 열기

목적지 없이 실행을 열면 반드시 내 차례(My turn)를 먼저 보여 줘야 한다(MUST). 대기 항목마다 반드시 카드 하나를 보여 줘야 한다(MUST). 같은 스냅숏에서 모든 소유자 할 일 건수는 그 카드 수와 반드시 같아야 한다(MUST). 대기 항목이 없으면 그 사실을 먼저 밝히고 짧은 진행 요약을 반드시 보여 줘야 한다(MUST). 결정 링크는 그 결정의 항목을 반드시 바로 열어야 한다(MUST). 카드는 반드시 두 묶음으로 나누어야 한다(MUST). 첫 묶음은 다른 작업을 기다리게 하는 항목이다. 계획 승인, 제출된 작업의 게이트 결정, 기다리는 하위 작업이 있는 계획된 허가, 키 복구가 여기에 든다. 둘째 묶음은 나머지 모든 카드다. 각 묶음 안에서는 요청이 기록된 시각이 가장 이른 카드가 반드시 먼저 나와야 한다(MUST). 복구가 필요한 요청은 DASH-R21에서 다룬다.

확인: B에는 결정 ID가 서로 다른 소유자 할 일 카드 두 개와 건수 2가 보인다. 대체된 승인은 나오지 않는다. 자유 질문에 답하고 새로 고친다. 카드 하나와 소유자 할 일 하나가 남는다. C에는 할 일이 없다는 안내와 진행 중인 작업이 나온다. E에는 할 일이 없다는 안내와 완료 결과가 나온다. D의 결정 링크를 열면 안내서 질문이 나온다. B의 자유 질문은 계획 승인보다 먼저 들어왔다. 계획 승인 카드가 먼저 나오고, 자유 질문 카드가 그다음에 나온다.

### DASH-R6 — 진행을 작업 목록으로 보여 주기

진행 화면은 작업마다 한 항목을 두고 그 상태와 기록된 담당자를 보여 주는 목록이나 표로 반드시 열려야 한다(MUST). 진행 화면은 배정되지 않은 작업과, 배정 기록에 신원이 빠진 작업을 반드시 구분해야 한다(MUST). 그래프와 기록 화면은 요청할 때 각각 별도 화면으로 반드시 열려야 한다(MUST).

확인: C에는 작업마다 한 행이 있다. 실행 중인 화면 작업은 기록된 배정과 함께 나오고, 제출된 API 작업은 검토 대기로 나온다. 배정되지 않은 작업과, 배정은 있지만 신원이 없는 작업을 비교한다. 내 차례, 진행, 그래프, 기록 화면을 차례로 연다. 작업 도식은 그래프에만 나오고, 전체 이벤트 목록은 기록 화면에만 나온다.

### DASH-R7 — 그래프와 진행 용어 설명하기

대시보드는 언어마다 한 상태에 한 용어를 모든 화면에서 반드시 써야 한다(MUST). 건수는 작업이나 전달처럼 무엇을 세는지 반드시 밝혀야 한다(MUST). 그래프는 보이는 작업 상태, 연결선의 뜻, 시간 표시를 설명하는 범례를 반드시 제공해야 한다(MUST). 위험도는 반드시 위험을 뜻하는 이름으로 표시해야 한다(MUST).

확인: C의 같은 시점에서 요약, 작업 행, 그래프를 비교한다. 작업 상태마다 같은 용어가 나오고, 합계는 이름 붙인 대상의 수와 같다. C에 렌더링된 모든 `data-relation`, 작업 상태 클래스, 재생 표시를 나열한다. 각각에 맞는 이름 붙은 범례 항목이 있다. 두 언어 모두 lane 2를 위험도 2로 표시한다.

### DASH-R8 — 반려된 시도 따라가기

소유자는 영향을 받은 작업이나 그 카드에서 기록된 반려와 그 수정판, 시도, 실패한 검사, 근거까지 반드시 찾아갈 수 있어야 한다(MUST). 대시보드는 그 이력을 현재 시도 횟수와 반드시 구분해야 한다(MUST).

확인: B에서 API 작업을 따라 수정판 1의 시도 1까지 거슬러 간다. 실패한 빈 검색어 검사와 기록된 결과가 나온다. 수정판 2로 돌아오면 고친 검사가 나온다. 현재 횟수가 초기화되었어도 첫 시도에는 원래 기준이 남는다.

### DASH-R9 — 구조 수정에 수정 노트 요구하기

구조 수정마다 `gf plan set <file> --note <json-file>`은 공백이 아닌 문자열 네 개(`reason`, `decision`, `if_approved`, `if_sent_back`)가 든 새 수정 노트를 반드시 받아야 한다(MUST). `decision`은 선택할 내용을 반드시 한 문장으로 밝혀야 한다(MUST). 트랜잭션은 받은 노트를 `plan.set.data.revision_note`와, DASH-R19에 따른 승인 요청에 반드시 기록해야 한다(MUST). 트랜잭션은 이전 수정판의 노트를 물려받거나, 실행 수준의 `context.why`를 노트로 써서는 안 된다(MUST NOT). 실행 맥락은 계속 계획 전체를 설명한다. 수정 노트는 구조 식별값에 영향을 주어서는 안 된다(MUST NOT). 입력이 없거나 올바르지 않으면 명령은 문제가 된 입력을 밝히고, 수정판을 쓰거나 승인을 대체하기 전에 반드시 거부해야 한다(MUST).

확인: 승인된 계획에서 검사 명령 하나를 바꾼다. 노트를 통째로 빼 본 다음, 각 부분을 하나씩 빼거나 비우거나 잘못된 형식으로 넣는다. 종료 코드는 0이 아니고, 입력 이름이 나오며, 계획과 이벤트의 바이트는 그대로다. 완전한 노트를 넣으면 새 수정판 하나와 그 승인 요청이 생긴다. 같은 계획 파일에 다른 구조 변경을 하고 노트 없이 게시한다. 이전 노트와 기존 맥락이 있어도 거부된다. 첫 계획을 노트 없이 게시하고 승인한 다음 똑같이 다시 게시한다. 새 수정판은 생기지 않는다. 제목만 고치면 검증된 승인을 다시 쓴다.

### DASH-R10 — 바뀐 내용보다 수정 노트 먼저 읽기

구조 수정에서 카드는 묶인 수정 노트를 ‘리더의 설명’(Leader’s explanation)이라는 이름으로 먼저 보여 주고, 서명할 질문을 그 제목으로 반드시 써야 한다(MUST). 그다음 카드는 바뀐 작업과 바뀐 계획 수준 필드만 보여 주고, 바뀌지 않은 나머지는 반드시 접어 두어야 한다(MUST). 변경마다 필드 이름과 이전 값·새 값을 보여 주거나, 추가나 삭제를 반드시 표시해야 한다(MUST). 바뀐 작업마다 별도의 ‘기록된 이력’(Recorded history) 구역에 가장 최근에 반려된 시도와 실패한 검사를 보여 주거나, 기록이 없으면 ‘반려된 시도 없음’(No returned attempt)이라고 반드시 밝혀야 한다(MUST). 버튼 옆의 결과는 DASH-R3을 따른다. 위험을 높이는 변경은 DASH-R22에서 정한다.

확인: B에서 수정 노트, API 검사의 이전·새 기준, 추가된 패키징 작업, 그리고 바뀌지 않은 작업을 담은 닫힌 펼침 영역이 차례로 나온다. 리더가 다른 이유를 써도 API 이력에는 시도 1과 실패한 빈 검색어 검사가 나온다. 추가된 작업에는 ‘반려된 시도 없음’이 나온다. 한 변형에서 반려 기록을 지우고 노트는 남긴다. API 작업에도 같은 빈칸 표시가 나오고, 작성자의 글은 바뀌지 않는다. 다른 변형에서는 작업 하나를 지우고, 또 다른 변형에서는 실행 수준 검사를 바꾼다. 지운 ID와 검사의 두 값이 나온다.

### DASH-R11 — 채팅으로 수정 내용 전달하기

구조 수정에서 성공한 `plan set` 결과는 수정판, 결정 ID, 저장된 노트 필드 네 개를 모두 반드시 돌려줘야 한다(MUST). 소유자를 그 승인으로 안내할 때 리더는 같은 노트를 전달하고, 채팅에서 그 수정판과 결정을 반드시 밝혀야 한다(MUST). 서명 동작은 반드시 소유자의 답변 화면에 남아 있어야 한다(MUST).

확인: B의 명령 결과를 그 `plan.set` 노트, 승인 요청과 대조한다. 수정판, 결정 ID, 네 문자열이 모두 같다. 사람의 판단: 이 결과로 채팅에서 수정 내용을 전달한다. 소유자가 계획을 다시 풀어 쓴 글을 읽지 않고도 결정, 이유, 두 결과를 찾는지 확인한다.

### DASH-R12 — 서명 버튼의 이름과 순서 정하기

모든 서명 버튼은 보이는 이름과 접근성 이름 모두에서 서명한다는 것과 그 결과를 반드시 밝혀야 한다(MUST). 같은 동작에는 결정 종류가 달라도 반드시 같은 말을 써야 한다(MUST). 해당 버튼이 있으면 화면, DOM, 키보드 순서는 반드시 ‘서명하고 돌려보내기’(계획된 허가에서는 ‘서명하고 허가 거부’), ‘서명하고 승인’(또는 그 종류의 긍정 답), ‘살펴보기’여야 한다(MUST). 보류(hold)나 기록된 실패가 있으면 수락 버튼에는 반드시 ‘실패가 있어도 서명하고 수락’(Sign and accept despite failures)을 써야 한다(MUST). 자유 질문의 선택지마다 그 답에 서명해서 보낸다는 것을 반드시 밝혀야 한다(MUST). 살펴보기는 반드시 구별되는 이름을 갖고, 답을 기록하지 않아야 한다(MUST).

확인: 픽스처 표의 결정 행마다 두 언어로 확인한다. A, B의 계획, J에는 ‘서명하고 돌려보내기’, ‘서명하고 승인’, ‘살펴보기’가 이 순서로 나온다. D, F, G, H, I, K에서는 부정 답, 종류별 긍정 답, 살펴보기를 화면·DOM·키보드 순서마다 대조한다. F와 실패가 있는 D 변형에는 위험을 알리는 말이 붙는다. B에서는 선택지마다 보이는 이름과 접근성 이름에 ‘서명하고 보내기’(Sign and send)와 선택지 원문이 들어 있다. 종류마다 살펴보기만 하면 답은 0개다. 이름 붙은 선택지 하나를 제출하고, 별도 픽스처에서 유효한 승인을 제출한다. 제출마다 검증된 답이 정확히 하나 생긴다. 선택지는 결과 `answered`와 고른 문구를 남기고, 승인은 `approved`를 남긴다.

### DASH-R13 — 읽기 조건 설명하고 적용하기

비활성 답 버튼 옆에 카드는 남은 조건과 그 조건을 채우는 방법을 밝히거나, 그 조건을 채울 수 없는 이유를 반드시 설명해야 한다(MUST). 조건을 하나 채울 때마다 안내는 반드시 갱신되어야 한다(MUST). 카드는 지정한 답을 활성화하기 전에, 아래 표에서 해당하는 조건을 모두 반드시 적용해야 한다(MUST). 실패가 기록되어 있으면 근거 상세만이 근거 읽기 조건을 채운다. 자료를 목록에 보여 준 것만으로 그 자료를 연 것으로 쳐서는 안 된다(MUST NOT). 계획 승인의 읽기는 DASH-R20에서 정한다.

| 입력과 답 | 필요한 동작과 바로 옆 안내 | 읽지 않은 픽스처에서 확인할 것 |
| --- | --- | --- |
| D, G, H, I · 근거가 있는 수락이나 허가 | 근거 상세나 목록의 파일을 연다. 파일이 없으면 근거 상세만 안내한다. | D의 사본에서 두 방법을 따로 쓴다. 어느 쪽이든 수락이 활성화된다. G, H, I에서는 픽스처 표에 적힌 자료를 확인한다. |
| F 또는 실패 기록이 있는 경우 · 수락 | 근거 상세를 연다. 수락 옆에 근거 상세를 안내한다. | 파일만 연다. 수락은 비활성 상태로 남는다. 근거 상세를 열면 수락이 활성화된다. |
| K · 판단할 자료 없이 수락 | 근거 없음 확인란을 직접 선택한다. 빠진 근거와 확인란을 안내한다. | 새로 고침을 기다린다. 확인란을 선택해야만 수락이 활성화된다. 결정을 다시 열면 확인란은 해제되어 있다. |
| 이유가 필요한 돌려보내기 | 바꿀 점을 공백이 아닌 글로 적는다. 계획을 돌려보낼 때 바뀐 항목이 있으면 각 항목도 연다. 계획된 허가를 거부할 때는 빈 메모를 허용한다. | B에서 바뀐 항목을 모두 열고 공백만 입력한다. 이유를 적으라는 안내가 나온다. 글을 적으면 돌려보내기가 활성화된다. D에서 글 확인을 반복한다. I에서는 빈 메모로도 거부가 된다. |
| 직접 쓰는 자유 답 | 공백이 아닌 답을 쓰거나, 서명 표시가 있는 이름 붙은 선택지를 고른다. | B에서 공백만 쓰면 직접 쓴 답의 제출은 비활성이고, 먼저 쓰라는 안내가 나온다. 글을 쓰면 제출이 활성화된다. 제시된 선택지는 자기 답을 담고 있다. |
| 읽는 중에 결정이 바뀜 | 새 결정을 확인하고 해당 읽기를 다시 한다. 바뀐 점과 남은 자료를 안내한다. | 읽는 도중에 D의 표시 근거를 바꾼다. 확인하고 다시 읽을 때까지 서명 버튼은 비활성이다. |
| 제출 때 표시가 오래됨 | 새로 고치고 현재 요청을 읽는다. | 이전 `displayed` 식별값을 `/api/answer`에 제출한다. `stale_decision`과 다시 읽으라는 안내가 나오고, 새 답은 0개다. |

확인: 행마다 새 픽스처 상태에서 시작한다. 동작마다 전후로 바로 옆 안내와 버튼 상태를 확인한다. A, B, J에도 DASH-R20에 따라 같은 확인을 한다.

### DASH-R14 — 읽기 쉬운 문서 형식 쓰기

대시보드는 밝은 모드와 어두운 모드를 반드시 제공해야 한다(MUST). 대시보드는 운영체제의 색상 모드 설정을 반드시 따라야 한다(MUST). 대시보드에 별도의 테마 선택 버튼을 추가해서는 안 된다(MUST NOT). 두 모드에서 버튼 옆 안내를 포함한 한글·라틴 문자 본문은 반드시 16 CSS px 이상의 크기와, 배경 대비 4.5:1 이상의 명암비로 표시해야 한다(MUST). 질문, 근거, 동작은 제목과 여백으로 반드시 구분해야 한다(MUST). 대시보드는 반드시 기울이지 않은 버튼과 무늬 없는 배경을 써야 한다(MUST). 대시보드 화면에서는 장식용 격자, 경고 줄무늬, 마스코트 그림을 반드시 빼야 한다(MUST). 기술 계측 정보는 반드시 기본 카드와 작업 요약 밖에 두어야 한다(MUST).

확인: 브라우저의 색상 모드 설정을 밝게, 다음에 어둡게 두고 B와 C를 두 언어로 캡처한다. 매번 설정에 맞는 테마가 나오고, 테마 선택 버튼은 없다. 본문과 안내의 계산된 글자 크기와 글자·배경 명암비를 확인한다. 버튼 글자는 가로로 놓이고, 장식용 마스코트 그림, 격자, 줄무늬는 0개다. 기본 요약에는 샘플링 안내와 밀리초 단위 검사 시간이 없다. 사람의 판단: 기본 배율에서 B의 질문, 이유, 안내와 C의 작업 상태, 담당자를 읽는다. 한글 글자 모양과 구역 사이의 구분을 확인한다.

### DASH-R15 — 두 언어로 화면 문구 제공하기

접근성 이름, 범례, 읽기 안내, 정보 누락 안내를 포함해 대시보드의 모든 문구에는 영어와 한국어가 반드시 있어야 한다(MUST). 대시보드는 작성된 질문, 노트, 근거의 내용을 반드시 그대로 보존해야 한다(MUST).

확인: 같은 원본 기록으로 A~K를 언어마다 렌더링한다. 동작과 이동 대상이 같다. 화면 문구 키마다 두 언어 모두 공백이 아닌 값이 있는지 확인한다. 두 렌더링에서 작성된 질문, 노트 필드, 파일 경로를 원본과 대조한다.

### DASH-R16 — 이전 실행 표시하기

대시보드는 기존 실행을 반드시 불러와야 한다(MUST). 대시보드는 기존 기록 줄을 고쳐서는 안 된다(MUST NOT). 프로젝트가 옮겨졌거나 근거가 바뀐 경우, 대시보드는 기록 계약에서 정한 대체 관측(supersession observation)을 덧붙여도 된다(MAY). 노트가 없는 이전 수정판에서는 노트를 ‘기록되지 않음’으로 표시하고, 확인 가능한 변경과 이력을 반드시 보여 줘야 한다(MUST). 원래 계획 목표나 추측한 신원을 빠진 이유나 요청한 쪽으로 내보여서는 안 된다(MUST NOT). [대체 관측](../../skills/graph-flow/references/records.md#L523)

확인: 노트 도입 이전 B를 원래 위치에서, 근거를 바꾸지 않고 이슈 #3 필드 없이 연다. 카드 두 개, 명시된 빈칸, 변경 비교, 반려 기록 링크가 나온다. 열기 전후 기록 파일의 바이트를 비교한다. 프로젝트를 옮기거나 근거를 바꾼 경우 원래 줄은 같은 바이트의 앞부분으로 남고, 정한 대체 관측만 뒤에 붙는다. 다시 읽어도 같은 관측은 중복되지 않는다.

### DASH-R17 — 로컬 답변 보호 유지하기

대시보드는 로컬 서버의 토큰 검사와 Host 검사, 기존 소유자 서명 경로를 반드시 유지해야 한다(MUST). 진행, 이력, 수정 노트를 보는 동작으로 작업을 허가하거나 답을 기록해서는 안 된다(MUST NOT).

확인: 격리된 서버 테스트를 쓴다. 토큰 없이 답변 엔드포인트에 제출하면 401이 나온다. 유효한 토큰과 거부되는 Host로 다시 제출하면 403이 나온다. 두 요청 모두 답을 남기지 않는다. 픽스처 화면 사이를 오가도 결정은 열린 상태로 남는다.

### DASH-R18 — 기존 실행 환경 유지하기

대시보드는 반드시 표준 라이브러리만 쓰는 Python과 일반 HTML, JavaScript로 실행되어야 한다(MUST). 대시보드는 새 런타임 의존성을 요구해서는 안 된다(MUST NOT). 선택 사항인 그래프는 저장소에 이미 포함된(vendored) three.js를 써도 된다(MAY).

### DASH-R19 — 표시한 수정 노트를 서명에 묶기
